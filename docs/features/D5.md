# Feature: D5 — Production deployment architecture

Status: **decided from repository evidence** (2026-10-01). This record closes the
open decision carried since the 30 September audit (P0-4) and
`docs/DEPLOYMENT_DECISION.md`, which stated the question but deliberately did not
choose.

## Decision

**Netlify is the production architecture.** Docker self-hosting remains a supported
alternative, not a competing production target. **Vercel is not a deployment target
and is not configured.**

This was decided from what the repository contains, not from preference. The
evidence is one-sided:

| Concern | Evidence in the repository |
|---|---|
| Build | `netlify.toml`: `command = "npm run build"`, `publish = "dist"`, `NODE_VERSION = "22"` |
| API runtime | `netlify/functions/api.ts` — the Express app wrapped in `serverless-http`, with `express` and `serverless-http` declared as `external_node_modules` and `esbuild` as the bundler |
| API routing | `[[redirects]]` `/api/*` → `/.netlify/functions/api/:splat`, `force = true` |
| Crawler surfaces | `/robots.txt` and `/sitemap.xml` redirect to the function **before** the SPA fallback, because both are generated from the database |
| SPA fallback | `/*` → `/index.html`, last in the redirect list |
| Scheduled work | `netlify/functions/daily-news-refresh.ts` with `export const config = { schedule: '@daily' }` |
| Security headers | `public/_headers`, kept identical to the Express middleware by `tests/headers.test.ts` |
| Asset caching | `/assets/*` immutable (content-hashed), `/index.html` and `/sw.js` `no-store` |
| Setup documentation | `docs/NETLIFY_PRODUCTION_SETUP.md` |

Vercel appears nowhere in the repository: there is no `vercel.json`, no `api/`
directory, and no cron configuration. The Vercel deployment check the earlier audit
observed was a commit status, not a configuration — and a status without
configuration cannot serve this application, because the API, the scheduled job and
the crawler surfaces are all Netlify-specific.

## Why Docker is an alternative and not a conflict

`Dockerfile` is a complete, coherent self-hosting path: multi-stage `node:22-alpine`,
`npm ci`, `npm run build`, non-root `USER node`, `EXPOSE 3000`, `CMD ["node",
"build/server.cjs"]`, with a `.dockerignore`.

It works because the same Express app does double duty. `server.ts` serves `dist/`
statically with an SPA fallback, and starts listening **only when `NETLIFY` is not
set** — so the container is a real web server and the Netlify function is the same
app behind `serverless-http`. There is one application, one header set (asserted
identical by `tests/headers.test.ts`), and two ways to run it.

What Docker does **not** provide, and would need if it ever became the production
target: a scheduler. The `@daily` newsroom refresh is a Netlify construct; on Docker
it must come from cron, a Kubernetes CronJob, or an external scheduler calling the
admin ingest endpoint. Until that exists, **the scheduled newsroom refresh and the
analytics retention prune do not run on the Docker path.** That is the one real
difference between the two, and it is why Netlify is the decision rather than a
preference.

## What would have to change for the alternative

Recorded so the decision can be revisited without re-deriving it:

- **Vercel:** add `api/index.ts` exporting the Express app, a `vercel.json` with
  rewrites for `/api/*`, `headers` for the security set, and a `crons` entry for the
  newsroom job. `public/_headers` would be dead weight.
- **Docker as primary:** add a scheduler for the daily job and the retention prune,
  put the security headers behind a reverse proxy or accept the Express middleware as
  authoritative (it already sets them), and add a readiness probe to the orchestrator
  (`/api/health/ready` already exists for exactly this).

## Configuration that must be true in production

Verified as present and correct in the repository:

- No `localhost` or `127.0.0.1` URL in any production path. The API base is resolved
  by `src/lib/apiBase.ts` from the request origin, so the browser never calls a
  hard-coded host.
- No development credential is committed. An unconfigured frontend deliberately falls
  back to an inert Supabase client (`src/lib/supabase.ts`) so a preview build cannot
  crash on load — and `getServerSupabaseKey()` rejects any key that is not a
  service-role key, so a browser key cannot be promoted to server use.
- Production headers are gated on `NODE_ENV === 'production'`; the development CSP
  that allows `unsafe-inline`/`unsafe-eval` for Vite HMR is behind the same check and
  `tests/headers.test.ts` asserts it cannot leak into the production branch.
- `/api/*` responses are `no-store`; private routes carry
  `X-Robots-Tag: noindex, nofollow`.
- Admin bootstrap is disabled unless `EDUREACH_ADMIN_BOOTSTRAP_EMAIL` is explicitly
  set (`tests/api.test.ts` asserts the fail-closed behaviour).

## Environment variables

The contract is machine-readable in `src/lib/envContract.ts` and printed by
`npm run prod:validate` (values are never shown). Summary:

| Variable | Required | Visibility | Secret | Purpose |
|---|---|---|---|---|
| `VITE_SUPABASE_URL` | required | client | no | Supabase project origin (alias `SUPABASE_URL` is **server-side only** — not inlined into the bundle) |
| `VITE_SUPABASE_PUBLISHABLE_KEY` | required | client | no | Browser key; public by design, subject to RLS |
| `SUPABASE_SERVICE_ROLE_KEY` | required | server | **yes** | Bypasses RLS; admin routes, newsroom, analytics, job log |
| `NODE_ENV` | required | server | no | Selects the strict production header set |
| `EDUREACH_SITE_URL` | recommended | server | no | Canonical origin for sitemap and metadata |
| `EDUREACH_NEWSROOM_USER_AGENT` | recommended | server | no | Identifies the crawler to publishers |
| `EDUREACH_ADMIN_BOOTSTRAP_EMAIL` | optional | server | no | Enables first-admin bootstrap; leave unset in steady state |
| ~~`WHATSAPP_API_ENDPOINT` / `WHATSAPP_API_TOKEN`~~ | removed | server | — | Retired with the unused `src/server/whatsapp.ts` (audit P2-3). Student-facing WhatsApp links are static `wa.me` deep links and need no credential. |
| `PORT` | optional | server | no | Standalone/Docker listen port |

The trap the contract encodes: `SUPABASE_URL` and `SUPABASE_ANON_KEY` satisfy the
**server's** read of the same values but are not inlined into the browser bundle.
Setting only an alias produces a site that looks configured and cannot reach
Supabase. `tests/prod-validate.test.ts` asserts each alias is labelled with the
visibility the code actually gives it.

## Known limitations

1. **Nothing here is deployed.** This record resolves the architecture from
   repository evidence; it is not evidence that a deployment exists or works. See
   `docs/operations/PRODUCTION_RUNBOOK.md` for the sequence and
   `docs/PRODUCTION_READINESS_AUDIT_2026-10-01.md` for what remains unverified.
2. **The scheduled jobs are platform-coupled.** Both the newsroom refresh and the
   retention prune currently depend on Netlify's scheduler. That coupling is the
   main reason the decision matters.
3. **Netlify function limits are not measured here.** Cold starts, timeout ceilings
   and payload limits for the full newsroom run are unknown until the job has run in
   production; the runbook makes that an explicit verification step.
4. **`public/_headers` is Netlify syntax.** On any other host the rules must be
   re-expressed, or the Express middleware must be authoritative end to end.
