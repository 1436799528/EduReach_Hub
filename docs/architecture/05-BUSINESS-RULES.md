# 05 — Business Rules

Rules the system must never break, with where each one is enforced. A rule that
exists only in the UI is not a rule.

## 1. Trust and content

| # | Rule | Enforced in |
|---|---|---|
| T1 | EduReach is never presented as an official body; every ingested article carries an independence statement and official actions link out | `src/server/newsroom/pipeline.ts` (`buildArticleBody`), article page |
| T2 | No fabricated content: no static news dataset, no invented institutions programmes, no placeholder CBT bank presented as real, no demo rows left published | `docs/DATA_SOURCES.md`; seeds are removed by `20260927000000_postmerge_data_control.sql` |
| T3 | Published content must have a source name, an HTTPS source URL, a category from the maintained list, and an editorial body | Quality gate (`qualityGate.ts`) and the admin CMS validation |
| T4 | Time-sensitive content expires. Expiry is computed from the **source** publication date using the category TTL | `expiresAtFor()`; TTLs 90–365 days by category |
| T5 | Expired content leaves the public feed but a direct link stays readable and is labelled expired | `/api/news` filter + `/api/news/:slug` status |
| T6 | A closed opportunity must never be listed as open | `close_expired_opportunities()` + public filter on `is_active`/`closed_at` |
| T7 | Tier 1 official sources may publish automatically only when the quality gate passes **with no warnings**; every other tier waits for a human | `classify()` + pipeline status decision |
| T8 | Two stories about the same event must not both be published | Five-signal dedupe + `news_articles.dedupe_key` unique index |
| T9 | EduReach stores headline, source summary, attribution and advisory — never a reproduction of the source article | `buildArticleBody()`; no full-text capture in `parse.ts` |

## 2. Examinations (CBT)

| # | Rule | Enforced in |
|---|---|---|
| C1 | Scoring is server-side only. Guests are scored by the server endpoint; students by RPC | `/api/cbt/guest-submit`, `submit_cbt_attempt_for_subjects` |
| C2 | Answer keys are never readable by the browser | `20260919_admin_cbt_production_hardening.sql` revokes client access to `exam_questions` |
| C3 | One in-progress attempt per student per exam; answers are upserted, never duplicated | `start_cbt_attempt_for_subjects`, `unique (attempt_id, question_id)` |
| C4 | Duplicate submission returns the existing result instead of creating a second attempt | Submit RPC + `/api/cbt/submit` |
| C5 | Attempts expire server-side; the client countdown is display-only | Attempt expiry columns + RPC validation |
| C6 | A student sees only their own attempts and results | Owner-scoped RLS |
| C7 | An exam may not start without a usable question bank; the student gets the honest "not ready" message | `content_integrity_report()` + `lib/errors.ts` mapping |
| C8 | Paper composition (English 60 / other subjects 40, subject alias normalisation) is decided by the server | Subject-aware RPCs |
| C9 | Guest scoring is rate-limited (30 per 10 minutes) | `RATE_LIMIT_RULES.guestCbtSubmit` |

## 3. Student services

| # | Rule | Enforced in |
|---|---|---|
| S1 | The service page states exactly what EduReach does (information, assistance, document collection, submission, redirect) and whether a fee applies | Service catalogue content; a service without a live workflow renders coming-soon |
| S2 | Statuses come from the fixed vocabulary: `submitted, reviewing, processing, awaiting_information, completed, closed, rejected, cancelled` | `service_requests_status_check` |
| S3 | Status changes are made by staff through the admin queue and are audit-logged | `/api/admin/service-requests/:id` + `admin_audit_log` |
| S4 | Every request has a unique reference code generated by the server/database | `service_requests.reference_code` |
| S5 | Requests are private to the owner and to processing staff; no public reference lookup exists | Owner-scoped RLS; public tracker RPC revoked |
| S6 | A student cannot submit the same request twice by double-tapping; the server is authoritative | Server-side duplicate protection + disabled submit |
| S7 | WhatsApp is a contact channel, never the system of record | `wa.me` deep links in `src/data/hubContent.ts`; `service_requests` is authority. (The unused outbound API module was retired — audit P2-3.) |
| S8 | "Awaiting information" must tell the student exactly what is missing | `admin_note` surfaced on the request |

## 4. Accounts and privacy

| # | Rule | Enforced in |
|---|---|---|
| P1 | `profiles.role` is never client-writable | `20260903_restrict_profile_client_columns.sql` + RLS `role = 'student'` on self-write |
| P2 | Only the minimum personal data is collected: name, institution, faculty, department, level, matric number where a service requires it | Profile completion form; no DOB/address/documents at sign-up |
| P3 | Auth responses do not disclose whether an account exists | `AuthPageV2` messaging; Supabase Auth |
| P4 | Governance tables (`news_sources`, `news_ingest_*`, `rate_limit_hits`, audit logs) are service-role only with RLS enabled and no browser policy | Migrations `20260930120000`, `20260919*` |
| P5 | Analytics carries no sensitive values; `metadata` must not contain personal data | `/api/analytics/event` allowlist + event contracts (AN-1 will document each event's payload) |
| P6 | Students will be able to export and delete their own data | 🔴 not implemented — PRIV-2 |
| P7 | A retention period is defined for analytics and audit data | 🔴 not implemented — PRIV-2 |

## 5. Abuse control and API

| # | Rule | Enforced in |
|---|---|---|
| A1 | High-risk endpoints are rate-limited durably (bootstrap 5/15 min, guest CBT 30/10 min, uploads 20/10 min, import 10/10 min, newsroom run 6/h, analytics 240/min, all `/api` 1200/min per IP) | `lib/rate-limit.ts`, `check_rate_limit` |
| A2 | Unknown `/api` paths return JSON 404 and never the SPA shell | `server.ts` catch-all |
| A3 | Errors returned to users contain no SQL, stack traces or internal identifiers | `lib/errors.ts` (`userFacingError`) |
| A4 | Business rules live server-side; the client only renders outcomes | All admin/service/CBT endpoints |
| A5 | Bulk import is bounded (2,000 rows/batch), validated per row, and reports per-row errors | `/api/admin/content-manager/import/:resource` |
| A6 | File uploads are admin-only, size-capped and restricted to the storage bucket policy | `/api/admin/uploads` (5 MB), Supabase Storage |
| A7 | Privileged actions are recorded in the audit log | `admin_audit_log(...)` |

## 6. Operations and observability

| # | Rule | Enforced in |
|---|---|---|
| O1 | The scheduled newsroom run must always produce a report (counts + errors), even when it fails | `news_ingest_runs` row written at start, updated at end |
| O2 | A run with unreachable sources reports them rather than silently succeeding with zero items | `perSource` outcomes + `sources_failed` |
| O3 | Liveness and readiness are distinct: `/api/health` (process) vs `/api/health/ready` (dependencies) | `server.ts` |
| O4 | Data quality is measurable, not assumed: the integrity report is the source of truth for content health | `content_integrity_report()` |
| O5 | Deployment has one documented target | `docs/DEPLOYMENT_DECISION.md` (open decision D5) |

## 7. Rules that would be easy to break

These are the ones a future change is most likely to violate. Any PR touching the
areas below must state how it preserves them:

1. Publishing immediately after ingest without re-checking the gate (T3, T7).
2. Making an alias the canonical URL, or indexing `/search` (IA policy).
3. Adding a service form for a service that has no defined workflow (S1).
4. Letting a content editor read `service_requests` (role separation).
5. Computing a CBT score or trusting a client-supplied score (C1).
6. Showing an article without provenance because the column was null (T3).
7. Adding an analytics event with personal data in `metadata` (P5).
8. Disabling the durable rate limiter "temporarily" in an environment (A1).
