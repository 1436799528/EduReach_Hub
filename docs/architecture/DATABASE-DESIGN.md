# DATABASE DESIGN — proposal

Status: **proposal** (Milestone 001). No migration has been written, generated or
applied. No hosted database was modified. The existing 84-file migration set was
read only to understand the current shape; the new schema deliberately starts a
fresh history.

Conventions used throughout:

- All ids are `uuid` (`gen_random_uuid()`, `pgcrypto`), never sequential, so ids
  leak nothing and are safe in URLs.
- All timestamps are `timestamptz`, stored UTC, generated by the database
  (`now()`), never by a client. Business decisions (deadlines, release times)
  always compare against `now()` in SQL.
- Money-like or score-like numbers are integers/numerics, never floats.
- Enumerations are Postgres `check` constraints in phase 1 (cheap to add), moved
  to lookup tables only where the set is data, not code.
- Every table has `created_at`, `updated_at` (trigger-maintained) unless stated.
- Soft delete only where operational history matters (`deleted_at`); users are
  never hard-deleted as part of a normal request (see `SECURITY-REQUIREMENTS.md` §7).
- Naming: plural snake_case tables, `<table>_<column>_idx` indexes,
  `<table>_<cols>_key` constraints.

## 2. Identity, users, roles

| Table | Key columns | Constraints |
| --- | --- | --- |
| `auth_users` | `id uuid pk`, `email citext unique not null`, `password_hash text` (only if option B auth), `email_verified_at`, `last_sign_in_at`, `disabled_at` | unique email; `disabled_at` blocks sign-in |
| `profiles` | `user_id uuid pk → auth_users`, `full_name`, `phone`, `school_id → institutions`, `programme_id`, `level`, `matric_number`, `avatar_url`, `profile_completed boolean`, `role app_role not null default 'student'` | `role` check in (`student`,`content_editor`,`service_admin`,`super_admin`); unique `matric_number` per institution when not null |
| `role_capabilities` | *(code, not table)* | The capability map is code (`src/lib/capabilities.ts` equivalent), versioned with the app, not editable data. Deliberate: a compromised admin cannot grant themselves a capability by editing a row. |
| `security_events` | `user_id`, `kind`, `ip_hash`, `user_agent_hash`, `created_at` | owner-read only |

Notes:

- `profiles.role` is the **only** authority for staff status; tokens never carry
  it. The column is not writable through any user-facing endpoint — role change
  is an admin capability with its own audit row, and self-change is refused in
  the service **and** by a database trigger (`guard_profile_role` equivalent).
- Email lives in `auth_users` and is exposed to the frontend through
  `GET /v1/me` only for the caller (and to admins with `user.read`).

## 3. Academic catalogue

| Table | Key columns | Constraints / indexes |
| --- | --- | --- |
| `institutions` | `id`, `name`, `short_name`, `state`, `type`, `city`, `slug unique`, `is_active` | `gin` index on `to_tsvector(name)` for search; unique `slug` |
| `programmes` | `id`, `institution_id`, `name`, `level`, `faculty` | unique `(institution_id, name, level)` |

stores subject as free text on `exam_questions`, which is why it cannot be
filtered reliably. Proposal: `questions.subject_id → subjects` with a
denormalised `subject_name` snapshot where display copy must not change.

## 4. Examination banks and classification

| Table | Key columns | Constraints |
| --- | --- | --- |
| `question_banks` | `id`, `title`, `exam_type_id`, `subject_id nullable` (null = multi-subject), `duration_minutes`, `total_marks`, `is_active`, `created_by` | check `duration_minutes between 1 and 360` |
| `bank_classifications` | `bank_id pk → question_banks`, `visibility` in (`public`,`restricted`), `correction_release_at timestamptz`, `classified_by`, `classified_at`, `updated_by`, `updated_at` | **no row = unclassified = fail closed**; check `(visibility='public' and correction_release_at is null) or (visibility='restricted' and correction_release_at > classified_at)` |
| `candidate_assignments` | `bank_id`, `user_id`, `assigned_by`, `assigned_at`, `revoked_by`, `revoked_at` | pk `(bank_id, user_id)`; index `(bank_id) where revoked_at is null`; check `revoked_at is null or revoked_by is not null` |

Rules encoded in the database, not the API:

- **Classification immutability**: `visibility` may be set once. Changing it needs
  a separately reviewed lifecycle migration; a trigger refuses
  `update of visibility` after insert. Rationale: relabelling a public bank as
  restricted (or vice versa) silently changes who can read historical content.
- **Release can move later, never earlier past `now()`**: a trigger refuses
  setting `correction_release_at <= now()` or moving it backwards once it has
  passed. Early exposure cannot be undone, so the database refuses to produce it.
- **A restricted bank cannot exist without the provenance guard**: a trigger
  checks the guard trigger exists and is enabled (carried from the candidate SQL).
- `for share` locks on `bank_classifications` are taken by authorization checks so
  a revocation/release change serialises against in-flight writes.

## 5. Questions, options, provenance

| Table | Key columns | Constraints / indexes |
| --- | --- | --- |
| `questions` | `id`, `bank_id`, `subject_id`, `stem text`, `explanation text`, `marks int`, `position int`, `difficulty`, `review_status` (`draft`,`needs_review`,`approved`,`rejected`), `source_type`, `source_name`, `source_url`, `source_year`, `import_id nullable`, `text_fingerprint text generated`, `created_by` | unique `(bank_id, position)`; index `(bank_id, review_status)`; **index on `text_fingerprint`**; check `marks between 1 and 100` |
| `question_options` | `id`, `question_id`, `label char(1)`, `body text`, `is_correct boolean`, `position` | unique `(question_id, label)`; **partial unique** `(question_id) where is_correct` |
| `question_provenance_events` | `id`, `question_id`, `bank_id`, `event` (`created`,`imported`,`moved`,`refused_copy`), `source_import_id`, `actor_id`, `created_at` | append-only; index `(question_id)`, `(bank_id, created_at)` |

Design decisions:

- **The answer key is a row property, not an array index.** The current system
  stores `correct_option char` plus four text columns
  (`option_a..option_d`). That cannot express 5-option questions, cannot enforce
  "exactly one correct", and couples the API to option letters. The proposal uses
  `question_options`, while the **API keeps exposing `option_a..option_d` and
  `correct_option`** for v1 compatibility (mapped in the service layer).
- **`text_fingerprint`** is a generated, normalised hash of the stem
  (lower-cased, punctuation collapsed, sha256). It backs the provenance guard:
  a question may not be created or edited into a non-restricted bank if an
  identical fingerprint exists in a restricted bank. A `before insert or update`
  trigger enforces it with a distinct error identifier, so the API maps only that
  refusal (see `API-CONTRACT.md` §6.3).
- **Provenance is a real column, not an inference.** `questions.import_id` and
  `question_provenance_events` record where a question came from. Historical
  questions are never auto-classified: a backfill, if ever needed, is a reviewed
  migration with an explicit source for every row.
- Statement-level work: no `delete from questions` route; removal is
  `review_status='rejected'` or an audited admin delete with a foreign-key guard
  when attempts reference the question.

## 6. CBT attempts

| Table | Key columns | Constraints / indexes |
| --- | --- | --- |
| `attempts` | `id`, `user_id nullable` (null = guest), `bank_id`, `mode` (`practice`,`mock`,`guest`), `status` (`in_progress`,`submitted`,`expired`,`abandoned`,`deleted`), `paper jsonb` (ordered question ids), `question_count`, `duration_minutes`, `started_at`, `deadline_at`, `submitted_at`, `revision int default 0`, `score int nullable`, `correct_count int nullable`, `request_key text` | unique `(user_id, request_key)` where `request_key is not null` (idempotent start); index `(user_id, started_at desc)`; index `(bank_id, status)`; check `deadline_at > started_at` |
| `attempt_answers` | `attempt_id`, `question_id`, `selected_index smallint nullable`, `updated_at`, `revision int` | pk `(attempt_id, question_id)`; FK question; check `selected_index between 0 and 9` |
| `answer_revisions` | `id`, `attempt_id`, `question_id`, `revision`, `selected_index`, `received_at`, `operation_key` | unique `(attempt_id, question_id, revision)`; retained for dispute resolution |
| `attempt_operations` | `id`, `attempt_id`, `operation_key text`, `kind` (`answer`,`finalize`,`start`), `payload_hash`, `response jsonb`, `created_at` | **unique `(attempt_id, operation_key)`** — this is the idempotency guarantee: a retried request returns the recorded response instead of writing twice |
| `writing_sessions` | `id`, `attempt_id`, `client_id`, `generation int`, `started_at`, `ended_at`, `ended_reason` | **partial unique `(attempt_id) where ended_at is null`** — at most one active writing session per attempt, enforced by the index, not by application logic |
| `attempt_results` | `attempt_id pk`, `score`, `correct_count`, `total_questions`, `breakdown jsonb`, `computed_at`, `released_at nullable` | one row per attempt, written only by the finalizer |

Transaction requirements:

1. **Start**: `select … from question_banks for share` → authorize → choose paper
   → `insert attempts` + `insert attempt_operations(start)` in one transaction.
   A duplicate `request_key` returns the existing attempt (200), never a second
   one.
2. **Answer save**: `select attempt for update` → verify status, deadline
   (`now() <= deadline_at`), writing session, bank access (bank policy row
   `for share`) → `insert answer_revisions` → `upsert attempt_answers` →
   bump `attempts.revision` → record `attempt_operations` response. All in one
   transaction; a duplicate `operation_key` short-circuits to the stored
   response.
3. **Finalize/submit**: `select attempt for update` → idempotent status check →
   mark session ended → score from `question_options` (server-side only) →
   `insert attempt_results` → update `attempts` → write audit row. One
   transaction; the attempt row lock makes concurrent submissions serialise, and
   the loser reads the winner's result instead of scoring twice.
4. **Expiry**: a job (or a guarded `update … where deadline_at < now()`) moves
   `in_progress` → `expired`; submissions after the deadline are refused with a
   distinct code, and drafts are preserved (no silent answer loss).

## 7. Results and history

- `attempt_results` holds the authoritative score; `attempts.score` is a cached
  copy updated in the same transaction (never independently).
- **Correction release**: results are readable only when the bank is `public`, or
  the bank is `restricted` **and** the caller holds an active assignment **and**
  `now() >= correction_release_at`. Enforced in the query, not in the client.
- History lists attempts with `score: null` where the result is embargoed — a
  withheld value is distinct from zero, which the current system also fixed and
  must not regress.
- `breakdown jsonb` stores per-question outcome (position, selected, correct,
  explanation) and is only returned after release.

## 8. Question imports and reviews

| Table | Key columns | Constraints / indexes |
| --- | --- | --- |
| `question_imports` | `id`, `bank_id`, `exam_type_id`, `subject_id`, `paper_year`, `original_filename`, `mime_type`, `file_bytes`, `checksum`, `storage_key`, `status` (`uploaded`,`extracting`,`extracted`,`reviewing`,`publishing`,`completed`,`failed`), `item_count`, `approved_count`, `imported_count`, `duplicate_count`, `uploaded_by`, `error jsonb` | unique `(checksum)` per uploader (dup upload detection); index `(bank_id, status)`; check `file_bytes <= 20 * 1024 * 1024` |
| `question_import_items` | `id`, `import_id`, `source_index`, `stem`, `options jsonb`, `correct_label`, `explanation`, `passage`, `issues jsonb`, `review_status` (`pending`,`approved`,`rejected`), `duplicate_of`, `question_id nullable` (set on publish), `version int` | unique `(import_id, source_index)`; index `(import_id, review_status)`; optimistic concurrency via `version` |

Transaction requirements:

- **Publication is one transaction**: lock the import row (`for update`), require
  `status in (extracted, reviewing)` and a classified destination, re-validate
  every approved item, insert questions + options, set `question_id` per item,
  update counters and status to `completed`, write the audit row. Any failure
  rolls back the whole batch — the current system's atomicity requirement.
- **Review is optimistic**: `update … where id = $1 and version = $2`; zero rows
  → `409 stale_review`.
- **A reviewed import may not be re-pointed between differently classified
  banks**: trigger on `question_imports.exam_id/bank_id` change.
- Import source files are private forever; the storage key is never returned to
  the browser (a signed, short-lived URL is).

## 9. Audit logs

| Table | Key columns | Constraints |
| --- | --- | --- |
| `audit_logs` | `id`, `actor_id nullable`, `actor_role`, `action`, `entity_type`, `entity_id`, `metadata jsonb`, `request_id`, `ip_hash`, `created_at` | append-only: `revoke update, delete` from the app role + trigger refusing `update`/`delete`; index `(entity_type, entity_id, created_at desc)`, `(actor_id, created_at desc)`, `(created_at desc)` |

Metadata is policy data only: visibility, from/to release times, candidate ids,
import ids, counts, result of the attempt. **Never** question text, option text,
answer keys, hashes of them, or student answers.

Two operational decisions are deliberately left open (owner, not engineering):
retention period, and whether audit rows must be exportable to cold storage.

## 12. Foreign keys and delete behaviour

- `profiles.user_id → auth_users` `on delete restrict` (deletion is a workflow).
- `attempts.user_id → auth_users` `on delete set null` + pseudonymisation, so
  statistics survive account deletion.
- `questions.bank_id → question_banks` `on delete restrict` (a bank with content
  cannot be removed silently).
- `candidate_assignments → bank_classifications` `on delete cascade` (an
  assignment cannot outlive its bank policy).
- `question_imports.bank_id → question_banks` `on delete restrict`.
- `attempt_answers.question_id → questions` `on delete restrict` while an attempt
  exists — a question that was served must not vanish from a historical paper;
  the alternative is a `question_snapshot jsonb` on the attempt (recommended if
  question deletion must stay possible).

## 13. Migration strategy

- **New history, no imports.** `drizzle-kit generate` produces numbered SQL files
  committed to `src/db/migrations`; applied with `drizzle-kit migrate`. The old
  `supabase/migrations` set is never replayed into the new database.
- `0001_init` is reviewed by hand: extensions, enums, helper functions, then
  tables in dependency order.
- Every migration is forward-only; corrections are new migrations. A migration
  that fails leaves the transaction rolled back (`drizzle` runs each file in a
  transaction).
- CI gate 1: `drizzle-kit generate` produces no diff for a clean schema (no
  hand-edited drift). CI gate 2: apply all migrations to an empty database, then
  run the integration and security suites against it.
- Backfill/data migration from the old database is **out of scope** for this
  milestone and requires its own plan, approval and rehearsal (the hosted lineage
  is unreconciled: 195 applied versions vs 84 files).
- Seed data (`db/seed.ts`) is synthetic only: one institution, one exam type,
  subjects, one public bank with three questions, one restricted bank with one
  question and one assigned candidate. Never production content.
