## Providers and sharing to verify

The architecture uses Supabase for Auth, database and Storage and includes Netlify deployment configuration (`netlify.toml`, `netlify/`). `index.html` requests Google Fonts from Google hosts, which exposes a visitor's network request to those hosts. External resources and WhatsApp links can direct users to third parties (`src/data/hubContent.ts`, `pages/StudentDashboardV2.tsx`); those destinations have their own practices. Confirm the actual hosting, Auth email sender, processors, sub-processors, regions, logs and contracts with the operator. Repository configuration alone is not proof of live processing or an exhaustive sharing list.

## Rights and controls actually available

The dashboard allows profile editing and individual saved-item and CBT-result removal. Security settings allow password changes, other-device sign-out and MFA; the cookie settings provide local preference controls while optional analytics is disabled. There is **no complete account-wide self-service deletion or export workflow** established in this repository. The dependency and backup implications are documented in `docs/audit/LAUNCH-USER-RIGHTS-AND-RECOVERY-2026-11-02.md`; direct Auth deletion is not a safe substitute. A monitored request contact, identity verification procedure, response process, retention schedule and treatment of backups/shared content must be determined and tested by the operator and counsel.

## Boundary for a future deletion and export service

The dependency matrix and proposed lifecycle in `docs/audit/LAUNCH-USER-RIGHTS-AND-RECOVERY-2026-11-02.md` are prerequisites, not an implementation. The current evidence is insufficient to safely implement either a complete deletion or a complete export locally: ownership, indirect identifiers, shared content, storage objects, real Auth behavior, backup handling and retention decisions are unresolved. In particular, Auth deletion cascades through CBT attempts and answers in `supabase/migrations/20260915_cbt_news_tables.sql` and can affect other shared records. No raw Auth deletion has been added.

A future reviewed design needs all of the following before it can represent a request as complete:

- **Identity and ownership:** derive the subject from a server-verified session, require recent reauthentication and explicit confirmation, and never accept an arbitrary user ID as authority. Separate administrative review with least privilege, audit, rate/origin protections, last-admin safeguards and ownership checks for every database row and Storage object. Protect other people's records and shared materials.
- **CBT and active work:** identify in-progress papers, writing sessions, pending answers and finalized results; decide with the operator how to handle them before changing anything. Prevent concurrent answer writes during execution and honor the authoritative scoring/deadline/recovery rules. Never claim pending local answers or other people's shared exam content have been erased merely by deleting an account.
- **Sessions:** define and test revocation of other sessions and the current session against the actual Auth provider, including failed/partial revocations and how request status remains accessible afterward. Clearing one browser alone does not revoke all sessions.
- **Storage and downstream copies:** inventory bucket objects, references and ownership, separate exclusive private data from shared or public content, and handle processors, logs and backups under approved rules. Do not delete a shared object merely because the account uploaded it. Define restore-and-reapply procedures.
- **Tracking, confirmation and retry:** make a request durable and owner-scoped, give a non-sensitive status/receipt and state the limits of the action. Use idempotent steps, checkpoints, locking and reconciliation across DB, Storage and Auth; explicitly represent partial failure, retry, cancellation and manual review. A click or accepted request is not proof of completion. Test interruptions after each boundary and concurrent/repeated requests.
- **Export:** define approved data categories, indirect identifiers and excluded third-party/shared data; check ownership server-side for each category, create a bounded private export with controlled access, verify completeness and failure states, and set actual expiry/retention only after an operator decision. Never expose answer keys or other users' content in an export.
- **Decisions and validation:** obtain operator/legal decisions for each retained, deleted or de-identified category, active requests, CBT records, audit logs, shared content, backups, processors, identity verification and the monitored request channel. Test with isolated multi-user data, partial failures and real provider behavior in an approved staging environment before offering the workflow. No timeframe, retention period or completion guarantee is inferred here.

## CMS / launch review

Existing `/privacy`, `/terms` and `/cookies` are served from admin-editable site content (`pages/LegalPage.tsx`); footer and cookie controls already link to them. The seed in `supabase/migrations/20261024120000_site_content_and_legal_pages.sql` is draft content and includes claims requiring verification, including age, retention and deletion. Live editor-managed text may differ. **Do not overwrite it with a migration or present a draft as verified policy.** Before publication, the operator and legal reviewer should:

1. Identify the controller/operator, verified contact and supported rights-request process.
2. Verify the data inventory, processors, cross-border transfers, access, cookies and live configuration.
3. Set and implement actual retention/deletion rules, including backups, audit records and shared content; test a safe request procedure.
4. Review privacy, terms and cookie language, age treatment and any lawful-basis/rights wording against applicable law and actual practices.
5. Update the existing CMS drafts, approve them and verify the deployed pages and links. Do not claim compliance, timelines, automatic deletion or capabilities the system does not provide.
