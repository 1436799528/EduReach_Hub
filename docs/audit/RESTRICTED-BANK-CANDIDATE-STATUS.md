# Restricted-bank implementation candidates — NOT RELEASE READY

The SQL files in `supabase/candidates/` are local experiments, not deployable migrations. **Do not apply them to any hosted or production database.** They do not collectively secure the application. The server now consults the candidate policy for guest questions/corrections and several other paths, but incomplete database and server integration means the application must not be used for confidential exams.

## What is locally prototyped

1. `restricted_bank_policy_foundation.sql` defines bank-level public/restricted policy, candidate assignments, staff-only classification/release/assignment/inventory RPCs, and predicates for access and correction release. No backfill occurs: no policy row means unclassified. The prototype makes classification immutable; a public bank cannot be relabelled restricted, nor a restricted bank made public, by these RPCs. It does not verify that an administrator's classification is factually correct or that a question was never previously disclosed. Only existing `cbt.manage` roles (content editor and super administrator, including documented legacy aliases) pass its database role check. The replayed baseline permits a `service_admin` to promote their own profile to `super_admin`; the candidate removes the table-wide profile UPDATE grant and restores previously specified profile-edit columns. This local mitigation depends on deployed role inheritance and grants being reconciled and has not changed hosted privileges.
2. `restricted_bank_readers_candidate.sql` wraps selected legacy question readers, subject availability, legacy/configured starts and owned paper readers. It revokes direct application access to the original unguarded reader functions and planner/plan-summary helpers. Those guards run in PostgreSQL, not in browser components.
3. `restricted_bank_results_candidate.sql` prototypes restricted pre-release suppression in configured and older submit wrappers, result/history wrappers, and a restrictive policy hiding the full direct `cbt_attempts` row before release. For an explicitly public bank, the local configured practice scoring/corrections remain visible. Restricted result data is only returned after release while an assignment remains active. This is a database experiment, not an integrated end-to-end guarantee.

4. `restricted_bank_admin_candidate.sql` adds the administrative layer. Audit triggers on `cbt_bank_security` and `cbt_bank_candidate_assignments` write classification, release, assignment, revocation and reassignment rows to `admin_audit_logs` (policy metadata only: visibility, timestamps, actor; never question text, answer keys or student answers), and `cbt_bank_admin_inventory`, `cbt_bank_admin_candidates` and `cbt_bank_admin_history` expose inventory, assignment state and the audit timeline to a re-verified bank manager. `cbt_bank_admin_assign` refuses an unknown account and records refusals. Publication is now guarded: the original `commit_question_import(uuid)` is renamed and revoked, and only `commit_question_import(p_import_id, p_actor)` is granted (to `service_role`). That wrapper re-reads the approving actor's role from `profiles`, takes a `for share` lock on the destination bank's classification, refuses an unclassified destination, publishes through the unchanged atomic function and writes the `bank_questions_published` audit row in the same transaction. A `before update of exam_id` trigger on `question_imports` refuses re-pointing a reviewed import between two differently classified banks. Classification itself remains immutable: no backfill, no promotion of an unclassified bank, and a public bank cannot be relabelled from these RPCs.

5. `restricted_question_provenance_candidate.sql` closes the copy path that classification alone cannot: question text that already exists in a restricted bank cannot be created or edited into a public or unclassified bank. It adds a database-side fingerprint that mirrors `questionFingerprint` in `src/server/question-import/validate.ts`, a `before insert or update of question_text, exam_id` trigger on `exam_questions`, a guard that refuses to create a restricted bank while that trigger is missing, and a `cbt_question_provenance_ready()` readiness marker. Nothing is backfilled, reclassified or attributed to a source bank, and copying public text into a restricted bank stays allowed. Server routes map the refusal to 403 with a `question_provenance_refused` audit row (question create/update) or `question_import_provenance_refused` (import publication), and no refusal message echoes the protected text. Paraphrase, pre-existing cross-bank duplicates and direct service-role writes remain outside its reach.

`scripts/rehearse-restricted-bank-concurrency.mjs` starts a private Unix-socket disposable PostgreSQL, applies every migration plus the candidates, and drives real Express handlers through a synthetic local PostgREST adapter using service-role privileges. It covers concurrent altered submissions, owner-only result reads, post-commit revocation, assigned/unassigned/revoked restricted v2 writing without scores, public/restricted/unclassified guest papers, submissions and anonymous setup metadata, and verifies the v2 finalizer is not executable by an application role. The BASE-1 schema audit now reports the three objects that only the candidates create; a reviewed deployable migration must exist before server code can reach them, and the audit fails if that list changes without review.

`tests/restricted-bank-policy-candidate.test.ts` replays all repository migrations and these candidates into disposable PGlite, sets real local PostgreSQL `anon` and `authenticated` roles and synthetic user claims, and exercises staff/nonstaff management, predicates, selected readers/starts, ownership, configured submission/retry, restricted score comparisons, direct attempt reads, history, before/after release, bank inventory and classification, assignment/revocation/reassignment, release configuration, publication into unclassified/public/restricted banks, publication authority, atomic rollback, import re-pointing, audit content and public practice. `tests/authorization.test.ts` additionally drives the real Express bank-administration routes against a synthetic PostgREST adapter and asserts that policy reads and writes carry the caller's token (never the service-role key), that unauthorized callers are refused before any database call, that database refusals are audited and that an absent policy schema fails closed. `tests/restricted-bank-policy-baseline.test.ts` independently demonstrates the pre-existing local role-escalation path without candidates. `tests/restricted-bank-existing-exposure.test.ts` continues to reproduce the unmodified application's disclosure; it deliberately does not apply candidates. These tests are not hosted Supabase Auth/PostgREST tests.

## Outstanding blockers

- **Guest/server integration:** `server.ts` guest question and submit handlers and the anonymous catalogue now check for explicit public classification before service-role question reads. A real Express/local adapter/disposable PostgreSQL rehearsal tests public, restricted and unclassified banks. The server fails closed when the policy schema is absent, so it cannot be rolled out independently of the reviewed database change and inventory. The subject metadata path uses caller-scoped assignment checks but still requires race testing.
- **Administrative surface:** `/admin/banks` (`pages/AdminBankSecurityPage.tsx`, `src/bank-security.css`) and `/api/admin/cbt/banks*` (`src/server/restrictedBanks/routes.ts`) now cover inventory, classification, correction release, individual assignment/revocation and the audit timeline. Reads and writes execute with the caller's own access token (`getUserScopedSupabase`), and every write RPC re-checks `cbt_bank_is_manager()` in PostgreSQL; the service role is never used to classify a bank, assign a candidate or change a release time. Capability checks alone are not treated as authority. There is deliberately no bulk assignment, no automatic classification and no classification edit: those need a separately reviewed lifecycle. Hosted Supabase Auth/PostgREST behaviour and the real Vercel preview are still untested, and the routes return 503 when the candidate SQL is absent.
- **More result channels:** v2 rehearsal now explicitly blocks restricted/unclassified banks in selected server and database gateways, while public v2 session/answer is locally exercised; restricted v2 is unsupported and further v2 replay/finalization paths remain unaudited. V2 creation remains disabled. The admin analytics response now substitutes a public-only average and the user-activity view withholds nonpublic scores, but their full HTTP/authorization matrix is not verified. Concurrent altered configured submissions are locally tested; operations overlapping release/assignment revocation commits are not. No complete score-secrecy claim is valid.
- **Mutation and import:** generic content-manager CBT operations now additionally require CBT capabilities, generic question bulk import is refused in favor of review, and the SQL candidate prevents moving an existing question row to another bank. The admin question update route now refuses any `exam_id` change, publication requires an explicit destination classification plus the approving administrator's authority, an invalid approved batch rolls back whole, and a reviewed import cannot be re-pointed between differently classified banks. Manual copying of restricted material into a public bank (through the composer, a new upload or an admin duplicate action) remains possible, because provenance is not tracked per question; bank homogeneity alone is therefore still insufficient.
- **Compatibility:** the prototype's direct-table RLS hides entire unreleased restricted attempt rows; current dashboard and result fallbacks directly query that table. HTTP submit/history now preserve null scores rather than converting them to zero, but the results UI does not yet provide a reliable pending-release experience. The candidate fixes the oldest public `submit_cbt_attempt` SQL ambiguity and tests that contract; its whole-bank scorer is explicitly denied for restricted banks. Restricted setup discovery and subject availability require further caller-scoped integration and race tests.
- **Restricted v2 writing only:** the session, answer, state and paper boundaries now use the fail-closed bank predicate, so an actively assigned candidate can open and write a restricted v2 paper, an unassigned or unclassified caller is refused, and revocation applies to the next operation. Writing responses carry a draft revision only — no score, correctness or key. **Finalization is not available**: no application-role gateway exists and the scorer stays revoked, so restricted v2 cannot produce a result. V2 creation remains disabled. A future finalization gateway must apply the correction-release and assignment checks before returning `v2_result`.
- **Release/revocation races:** a concrete gap was found and fixed. The guarded wrappers checked `cbt_bank_candidate_access` in an earlier statement than the write they protect, so under READ COMMITTED a revocation committed between the check and the write still let a draft, answer or submission commit. This was reproduced with a barrier trigger on disposable PostgreSQL: the revocation committed while the write was in flight, and the write still returned `accepted`. The fix is `cbt_bank_lock_candidate_access`, a volatile predicate that takes a share lock on the policy row (and on the caller's live assignment row) before delegating to the internal function; every write wrapper now uses it. The guarantee is explicit: **a revocation or correction-release change never commits between an operation's authorization check and that operation's commit.** An operation that was already authorized may finish, and every later operation is denied, so revocation is serialized rather than instantaneous. A correction-release change is a policy write and therefore contends with the same lock, so an in-flight submission can only be wholly embargoed or wholly released. Read paths keep the single-statement predicate, which is already atomic with the read. Verified by disposable-PostgreSQL rehearsal for an in-flight v2 answer, an in-flight configured submission, the release transition, revocation after release, and reassignment. The new regression test fails if the lock is removed. Hosted concurrency, replication lag on a read replica, and administrative CRUD/import/publication remain unverified.
- **Dashboard contract:** result and history endpoints now distinguish withheld values from zero, but the dashboard/result UI still treats a hidden restricted attempt as missing, and `get_cbt_result` returns no rows before release. A reviewed pending-release UI and any dashboard aggregate adjustment remain outstanding.
- **Management and audit:** classification, assignment/revocation and release changes now have reviewed server/API workflows and database-written audit rows; the HTTP layer adds refusal audits (`bank_classify_denied`, `bank_assign_denied`, `question_import_commit_refused`, `question_import_bank_move_refused`, `question_bank_move_refused`). Audit rows hold policy metadata only. The database role mapping on the target is still unverified, the audit table's retention/immutability policy has not been reviewed operationally, and the chosen immutable classification lifecycle still needs sign-off; an early release or previously disclosed content cannot be made secret again.
- **Deployment and rollback:** review actual hosted grants, policies, schema, row ownership and role privileges. Test the full migration on approved disposable/staging infrastructure. A mixed-version deployment or server code running against an incomplete schema can disclose restricted data or break public practice. No production or staging state was inspected here.

## Staged inventory approach (not run against hosted data)

1. In a separately approved staging copy, reconcile schema, grant/role state, existing attempts, data ownership, and every access path. Inventory bank IDs, question counts, attempt counts, active usage and provenance. Guest access is not captured by these counts and prior disclosure cannot be disproved from them.
2. An authorized administrator reviews each bank and explicitly confirms public practice or restricted material, with an appropriately safe release time and individual candidate assignments for restricted banks. Never infer classification from active status, review status, source or prior exposure. Use fresh undisclosed material for secrecy. Unclassified banks remain unavailable at cutover.
3. Before any rollout, verify all approved public banks still support guest practice and corrections and all restricted banks deny guests/unassigned students. Validate in-progress/legacy attempts and agree on handling unclassified historical results. Coordinated readiness checks must prevent old service-role or RPC paths from operating against the new policy.
4. Only after complete local role/API tests, staging Auth/PostgREST tests, operator approval and a documented deployment plan should a reviewed migration be prepared. Preserve questions, attempts and answers; do not silently reclassify existing records.

No hosted service was contacted, no production data or policy changed, and no candidate was put in the deployable migrations directory.
