## Agreed decisions

1. Older clients must be explicitly refused when accessing or starting over a v2 attempt. Existing v1 attempts and their behavior remain unchanged; no active attempt is silently converted or cancelled.
2. Strict global protection for submission: all registered editing participants must be provably drained and stopped. An unavailable participant may block even timed submission. The precise participant protocol still needs a correctness design and proof; merely expiring a lease or checking one browser's IndexedDB is not proof of global quiescence. Existing answer deadline and 120-second submission grace remain unchanged.

A local intent on an offline device is not visible to PostgreSQL or another browser. Under strict protection, a device must register before editing; finalization must freeze new participants and wait for authenticated, durable drain-and-stop acknowledgements from all participants. A browser cannot acknowledge until it has durably stopped accepting intents and drained its own work; crash, lost acknowledgement and offline reopening must be handled without inventing quiescence. An unresponsive device remains a blocker, not an automatic timeout success. The design must also prevent a previously stopped client from creating new unregistered intents. This guarantee assumes correctly behaving supported clients; malicious or obsolete clients and database owners require separate threat-model controls. The protocol is not yet implemented or proven.

## Single target architecture

- **Per-attempt identity:** immutable server/database-owned v1/v2 discriminator; pre-existing attempts remain v1, with no record or deadline rewrite. An authorized v2 creation operation freezes the paper, initializes revision zero and coordinates creation/resume with the one-active-attempt invariant. Old and new start paths must refuse cross-protocol interference under concurrent starts.
- **Additive database compatibility:** retain v1 functions and grants; introduce version-aware protection against legacy snapshot and lifecycle changes to v2. Protect both `cbt_attempts` and `cbt_answers`, including start, expiry, abandon, delete and scoring, not merely draft RPCs. No global replacement or broad revocation. Proposed defense in depth is a PostgreSQL row/lifecycle guard plus a tightly scoped NOLOGIN executor role for owner-authenticated v2 functions, with catalog, role-membership, `SET ROLE`, trigger and service-role tests. If the hosting privilege model cannot enforce it, resolve that incompatibility rather than assume it works. Database owner/superuser DDL remains an explicitly controlled operational trust boundary.
- **Authorization and operations:** user-scoped token, owner check and frozen question membership for each read/write; no service-role fallback. One server-authoritative attempt-wide revision. Under the attempt lock, validate post-lock wall clock, immutable operation ID and request, expected revision and status; atomically update answer, revision and ledger. Same key/same payload replays; different payload fails; stale new key produces explicit conflict. Different-question stale operations can conflict.
- **Durable intent and reconciliation:** extend the existing account/attempt-scoped IndexedDB journal, not a second visible answer store. Persist an intent before claiming local capture. Bind the serialized head to a server revision and immutable wire operation before first transmission; unknown responses resend exactly that operation. Use one coordination discipline and transactional journal generations; Web Locks and notifications are coordination/invalidation tools, not server authority. Reconcile authoritative state and unresolved intent repeatedly; validate account, attempt, paper, generation and async responses. React, IndexedDB and PostgreSQL do not share a transaction.
- **Conflict handling:** retain local proposal and server answer, require explicit reviewed resolution, and create a new operation only after a deliberate keep-local decision; if the reviewed server revision changes, review again. Unknown response never gets a new key.
- **Submission:** only after answer persistence and recovery are proven, freeze registration and require the agreed strict participant quiescence. Persist immutable finalization ID; score only accepted server state under the same lock with post-lock deadline and existing 120-second grace. Duplicate finalization replays. An unavailable participant can prevent finalization, including timed auto-submit; no false completion claim or silent discard.
- **Rollback:** stop new v2 creation first; retain v2 fence, ledger, accepted data and compatible reader/writer/finalizer for active v2 attempts, or keep them explicitly read-only for recovery. Do not revert to a server that treats v2 as v1. A destructive schema rollback requires separately approved drain, backup and restoration plan.
