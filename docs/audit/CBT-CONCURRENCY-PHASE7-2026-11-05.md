## State model and current page behavior

The intended model is documented beside the page's existing `answers` state: the **server snapshot and revision are authoritative**; the journal holds durable unconfirmed/acknowledged operations; and `answers` is the sole **visible projection**, which may include a local unsaved selection. A local projection is never itself proof of a save.

For an advertised v2 paper, `load` now fetches the owner-scoped v2 state, obtains the current account's journal through the shared read-only IndexedDB path, and checks frozen paper order, positions, existing operation question IDs, options and server draft. It checks the current account and load generation before validation. Storage failures produce a specific browser-storage warning; unavailable/inconsistent state and successful preflight alike remain blocked by `CbtProtocolUnavailableError`. The page does not retry, send, mark, alter or project journal operations. Opening an empty IndexedDB database can create its schema, but does not create answer operations. A previously dispatched legacy request cannot be recalled by a later guard.

The v2 state endpoint now returns `questionIds`, preserving the same frozen list and question counts. The client rejects missing, empty, invalid or case-insensitively duplicate IDs and draft positions beyond the paper. `validateCbtJournalPaper` expects a snapshot already structurally checked by `fetchCbtV2State`; it validates paper ordering and journal position/question consistency. The server's local-only gate is unchanged. A loopback service could proxy hosted data, so the gate does not prove the target disposable; never connect it to real data. Older local v2 servers lacking the new field fail closed.

## Ordering and recovery gap found

The Phase 6 queue could retry a newer same-question operation while an older one was pending or conflicted. A deterministic test reproduced an accepted later write despite an unresolved earlier conflict. `retry` now checks the persisted sequence while holding the existing account/attempt Web Lock and refuses a later operation on that question until the earlier pending/conflict is resolved. It does not block an independent question. Two red tests first failed against the prior implementation and then passed. A further red test exposed UUID letter-case bypass of this ordering check; the comparison now treats question IDs case-insensitively. The replay-after-later-edit test now represents a separate browser/device journal, retaining the original test's newer-server replay assertion rather than bypassing the ordering rule.

This repair does not solve the whole session lifecycle. A scheduler must establish trusted acknowledged bases and current state, reconcile chains of pending/conflicted operations without discarding either intention, distinguish changes made during an in-flight request, and expose correct status. Multi-tab Web Locks are coordination, not server authority. Active-tab notifications and authoritative refresh are absent; there is no automatic replay on refresh, online or tab closure in the real page. IDB can be unavailable, corrupted, evicted or cleared. Legacy localStorage snapshots have no trusted revision/base and are not imported. The account-to-token binding across identity changes and frozen-paper changes by privileged writers also require end-to-end review before enabling writes. IndexedDB's account/attempt scope index still matches UUID strings case-sensitively; a differently cased attempt URL or older journal scope could hide pending records. Safe canonicalization and handling of existing variants are unresolved, so this is another reason not to enable projection or replay.

## Legacy / v2 separation and submission

Explicit v1 sessions retain `queueSave` → `saveConfiguredCbtDraft`, navigation snapshot flush, legacy recovery and snapshot submission. They remain concurrency-unsafe. For v2, preflight ends at the guard: no radio options, v2 operation, legacy answer/progress snapshot, or legacy submit is sent by the tested page. Missing/malformed metadata also fails closed. This is a negative safety boundary, not an integrated v2 answer path. Old clients, direct legacy RPCs and privileged writers remain able to bypass the isolated v2 candidate. Manual/timed v2 finalization is not implemented and remains blocked.
