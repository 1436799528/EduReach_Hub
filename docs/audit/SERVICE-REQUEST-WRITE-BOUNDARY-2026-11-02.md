## Evidence and limits

- Before the fix, the new local test observed authenticated UPDATE privilege and demonstrated that a privileged update can leave `updated_at` unchanged. Prior read-only production metadata independently showed the direct staff-update policy and grant; no hosted record was changed.
- Local role tests use a real PostgreSQL engine (PGlite), test synthetic students and staff, and model Supabase's service role as `BYPASSRLS`. They test direct column grants, inherited-grant failure, student ownership, service-role updates and stale compare-and-set. The service API tests use a mocked backend; they are not real hosted Auth, PostgREST or end-to-end tests.
- After the change, the local full suite passed **770/770** tests; typecheck, schema, 76-migration checklist, RLS, analytics and static accessibility audits and dependency audit passed. The local unconfigured build and performance budgets passed; Chromium desktop/mobile passed **178 tests, 2 skipped**, and the separate mobile performance test passed. The unconfigured server logs missing Supabase admin configuration, so these results are not hosted journey evidence. A local backup rehearsal applied 76 migrations and restored synthetic rows, but did not restore a production Supabase backup.
- A timestamp trigger invalidates an observed version after an intervening UPDATE, including note-only writes. It **does not** force privileged writers to use CAS or enforce valid transitions. It cannot ensure delivery or transactional atomicity of audits and notifications. More restrictive database roles/RPC design may still be required.
- `updated_at` now has microsecond precision and is set by the database regardless of a writer-supplied timestamp. The API must preserve the exact PostgREST version string, and old/deployed clients must be refreshed if they do not supply it. An existing non-finite timestamp aborts its update. Future-dated timestamps remain monotonic rather than being reset backwards. A competing trigger that changes the same field could invalidate the guarantee; inspect all hosted triggers and their execution order.

## Additional P0: student fields and direct staff reads

Before the second fix, a synthetic PGlite test found that an authenticated student could insert an otherwise-valid own request with a chosen `admin_note` and `updated_at = infinity`, and could read `admin_note` using table SELECT. A separate test showed that a staff account could read another student's request directly through `service_requests_read_staff`, bypassing the server's capability checks. Hosted behavior remains unverified; review existing affected records without assuming they are malicious.

The local, uncommitted `20261102200000_service_request_student_field_boundary.sql` candidate replaces client table-wide SELECT/INSERT with explicit column allowlists, preserves own-request/active-service RLS and removes the staff-read policy. It aborts on unexpected inherited privileges or unreviewed client-reachable SELECT/INSERT policies instead of deleting them. Existing client consumers use exactly the allowed projections; service-role reads and writes remain available to the existing admin API. Focused local tests cover each server-managed insert field, own-request tracking, other-student and direct-staff isolation, active-service and status rules, inherited privileges, unknown policies and service-role access. Read-only release and RLS checks now inspect column grants as well as table grants.

This is not proof of hosted PostgREST compatibility or full confidentiality. Unknown integrations, functions, policy expressions and role membership need explicit staging inventory and testing. Historical forged/infinite-version rows are not automatically changed; any remediation requires separate review and approval. Privileged writers can still bypass the API, and audit/notifications remain nontransactional.

## Mandatory rollout gate — not authorization to apply

1. Review actual migration ledger and schema drift, backup/restore readiness, locks, all table and column grants, inherited memberships, RLS policies, `service_role` privileges, triggers and timestamp types/values in a disposable/staging copy. The migration intentionally aborts atomically if the client roles retain UPDATE through inheritance; resolve the membership deliberately rather than bypassing the check.
2. Identify all direct database/PostgREST, scheduled, external and service-role writers and their owners; update or retire incompatible direct-client writers with explicit approval. Identify audit/notification dependencies and recovery steps. Do not infer their absence from this repository.
3. Rehearse migration ordering against staging with production-like schema and representative synthetic data, without replaying unsafe historical data mutations blindly. Exercise real authenticated students and all staff roles, the capability-checked API, status transitions, stale note/status races, microsecond round-trips, notifications, auditing and unavailable dependencies. Inspect the read-only validation outputs. Check deployed API compatibility before denying client writes.
4. Document a tested incident/rollback plan. Do **not** automatically regrant authenticated UPDATE: that reopens the known bypass. If a defect requires intervention, pause affected request processing, retain evidence and use a reviewed forward fix or controlled rollback under change approval, then re-run security checks. Dropping the version trigger alone weakens stale-write protection.
5. Obtain review, passing current-branch CI and preview, staging/UAT sign-off, owner/security approval and separate production change authorization. No merge or deployment is authorized by this document.

## Separate historical-data risk found in this audit

`20260916000000_application_integration_seed.sql` historically seeds prototype news and a demo CBT bank. `20260927000000_postmerge_data_control.sql` later deletes news by a set of slugs or prototype-body text and deactivates demo-labelled banks. The broad slug condition could match a genuine replacement on an existing database, and the demo bank/questions may remain as inactive records. Do not rerun these historical data migrations against populated projects blindly; reconcile ledger and inspect candidate records and dependencies before any owner-approved change. This finding does not establish what currently exists in production. The optional new placeholder-news seed was removed locally; that does not erase historical seed migrations or prove production content is clean.
