## Version and cutover contract

**No silent mixed-mode writing.** A v2 request must declare protocol `2` in a request body or dedicated header and supply both expected revision and idempotency key. The server must validate it and return an explicit unsupported/upgrade-required response for missing/unknown versions after activation; it must not infer a revision or generate an operation key for a legacy snapshot. Reads must return protocol capability, authoritative revision and draft in one consistent database snapshot. Candidate RPC names are experimental and do not establish this API.

A candidate operation key binds owner, attempt, kind, expected revision and payload. A retry after an unknown response uses exactly the same key and payload. A conflict consumes the key and requires explicit reconciliation and a new key. Replayed acknowledgement includes its accepted revision **and the current revision/draft**, so an older acknowledgement is never presented as the latest state. The client retains per-tab unsaved intent separately from the acknowledged server state. It must not mark it saved until accepted/replayed and synchronized; localStorage is not atomic across tabs. Cross-tab messages are advisory; the database remains authoritative.

## Proposed deployment order — gated, not yet demonstrated

1. Inventory active accounts/attempts **without answer contents**, all actual DB roles, role membership, jobs, server deployments, Edge Functions and direct RPC clients. Establish backup/restore and controlled administrative access. Verify operational ownership and student communications. No production changes are approved by this design.
2. In disposable staging, validate migration against representative *synthetic* historical, in-progress, null/malformed-draft and completed attempts, actual PostgreSQL concurrency, real Auth/RLS and old/new client combinations. Record schemas, grants, trigger behavior and migration ledger; test restore/forward recovery. Do not infer success from a clean migration replay alone.
3. Arrange a scheduled CBT maintenance window **before any new examination begins**. Stop new starts at every entry point, including directly executable start RPCs and other privileged writers, with an audited server/database gate. Allow already-running legacy attempts to finish naturally using their existing deadline and 120-second grace. Do not shorten, lengthen, cancel, auto-submit or migrate active attempts without an approved student-safe policy. Wait for the existing deadline plus grace and in-flight requests to drain, then prove no in-progress legacy attempt or executing legacy write remains under a controlled database fence. If this cannot be proved, **abort**. Unsent/offline browser edits may still exist; explain that they are unconfirmed and cannot be automatically imported as accepted answers. Provide reviewed recovery/support rather than inventing intent.
4. While the fence and maintenance gate are active, apply a **reviewed future migration**, install controlled expiry/lifecycle paths, version protocol and privileges atomically, and verify all effective grants and writers before reopening. A version-capable API/client must already be deployable and verified; the gate prevents mismatched app/database versions serving CBT. Unknown privileged writers, invalid drafts or unexpected active attempts block activation. The current Phase 2 candidate is not this migration.
5. Verify exact app version, API version and DB capability; open only v2 CBT starts. Reject old HTTP and direct-RPC snapshots explicitly. Keep legacy browser drafts intact for manual review, not automatic replay. Monitor conflict and failure rates without logging answers or keys. A versioned client encountering an old-format attempt with a valid accepted server draft needs an audited transition or continued drain; malformed/unknown drafts require manual review and no writes. Closed/submitted historical results must remain unchanged.

The conditions above currently have **not** been met; they are a proposal, not permission to deploy. In particular, a maintenance gate that also blocks direct RPC callers and privileged jobs has not been implemented; old tabs can be offline; service-role and owner-level integrations are not fully inventoried. Therefore no safe mixed-version cutover is demonstrated.

## Pending writes and submission

Before manual submission the client must finish/retry known queued writes with their original operation keys and resolve conflicts; it must not pretend a timeout means rejection. The finalizer uses only the server draft under the attempt lock and expected revision; another accepted write before that lock produces a conflict. Once time is up the server rejects new answer operations at actual post-lock time, while a finalization may arrive until the unchanged `cbt_submit_grace()` boundary. A delayed pending answer that missed the deadline is unaccepted, remains visible as such, and must not be smuggled into the scoring snapshot. Timer-driven behavior and handling an unresolved conflict at deadline require explicit UX/product review; never choose a conflicting answer silently or claim it was accepted. Duplicate finalization and lost responses must replay the stored result without regrading.

## Rollback / incident recovery

Never re-enable old snapshot writers against v2 attempts, even as a quick rollback. Preferred recovery is a forward fix while the CBT gate remains closed. Any database rollback requires a separately tested restore/forward migration that preserves authoritative drafts, revisions, operation records and results, together with a verified compatible app; restoring a backup can lose later accepted work and requires an explicit RPO/reconciliation decision. Do not drop revision or operation data or return to legacy write privileges just because the UI is rolled back. Define on-call ownership, stop conditions and evidence before a release.

## Implementation and verification log

The design above was recorded before this implementation. No section is an approval to deploy.

- **Partial backend/database integration only:** `20261104120000_cbt_owner_expiry.sql` adds an owner-scoped, row-locked function, without changing existing records, legacy privileges, table RLS or snapshot RPCs. It checks wall-clock time after locking and marks an in-progress attempt expired only after the existing `cbt_submit_grace()`; it changes no answers, score, deadline or submitted row. `server.ts` now invokes it with the authenticated caller's RPC client on the exact database expiry refusal, rather than issuing a service-role table update. If the function is missing or fails, the server does not fall back to a direct write. The application must be released migration-first if this partial change is ever authorized; without the function expiry marking does not persist, though the answer RPC still refuses the write. Other service-role and privileged table writes remain possible.
- **Unintegrated candidate hardening:** `supabase/candidates/cbt_revision_protocol.sql` now refuses malformed old draft values and missing, duplicate or invalid frozen paper IDs before modifying or scoring an active attempt. It does not repair, discard or decide what the student meant. It still deliberately revokes legacy writers in its isolated rehearsal and is NOT the integration migration.
- `tests/cbt-owner-expiry-compatibility.test.ts` applied the additive expiry SQL over synthetic pre-existing in-progress (including empty and malformed-object drafts), expired and submitted attempts and compared the data, old grants, indexes and triggers before/after. Null draft is excluded by the replayed `NOT NULL` constraint; an object with invalid values is possible and was preserved rather than normalized. This validates **only the expiry addition**, not active-attempt v2 conversion. The synthetic platform shim differs from observed live service-role EXECUTE privileges; unchanged local grants do not prove live grants.
- Focused backend authorization, owner expiry and grace tests: **34/34 passed**. Candidate plus migration compatibility tests: **8/8 passed**. A red test reproduced accepting a malformed old draft before the candidate validation. Separate PostgreSQL sessions after 79 synthetic migrations passed the existing revision/deadline/grace races plus expiry-versus-finalization in both orderings. These tests neither integrate the real CBT client with v2 nor test hosted systems.
- The first full local CI run stopped on four regressions: the migration count in two runbooks, the missing migration in the release-sync check, and an obsolete source assertion for direct expiry. They were corrected, with the release-sync guard additionally testing anonymous-execute drift. The rerun of the affected tests passed **33/33**. The full `npm run ci` then passed: **814/814** Node tests, 79-migration checklist, typecheck and audits, build/performance **10/10** (334.6/336 KB gzip), desktop/mobile Chromium **194 passed / 20 skipped**, mobile performance **1/1**, accessibility **0 blocking / 5 informational**, dependency audit **0 vulnerabilities**. These browser tests exercise the existing client, not v2.
- A separate synthetic backup/restore rehearsal passed after **79 migrations**, with 50 tables, 593 columns, 53 policies and 50 tables with RLS; it is not a Supabase backup, production restore or v2 rollback rehearsal.
- `supabase/ci/production-validation.sql` checklist lists the additive expiry migration. The phase 2 candidate remains outside `supabase/migrations`; no deployable full v2 integration migration or rollback has been prepared.

## Remaining blockers

The actual answer and submit endpoints and client still use unversioned snapshots; direct authenticated legacy RPCs and service-role writes remain usable. There is no v2 API handshake, persistent operation queue, multi-tab conflict UI, coordinated cutover gate, compatible full integration migration or safe rollback rehearsal. The exact handling of unsent old-tab work and unresolved timer-driven conflicts needs product/operator review without extending deadlines. Browser tests of an integrated v2 client and staging/hosted verification have not run. **NOT READY.**
