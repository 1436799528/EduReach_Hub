# CBT pre-merge regression and security audit — 2026-11-07

The local implementation and its safety checks are not evidence of real Supabase Auth, JWT verification, PostgREST schema-cache behavior, hosted role graphs/RLS, staging performance, deployment or production behavior. Do not enable global v2 or public finalization. The current v2 app routes are restricted to loopback rehearsal and require a separately reviewed, authorized staging path.

## Migration-before-app dependency

The paper endpoint reads `cbt_attempts.protocol` for **both** protocols before routing. The prerequisite is `20261107120000_cbt_attempt_protocol_fence.sql`, including the column **and** the complete fence, not merely the column. Application rollout must follow a reviewed, applied and independently verified migration/schema/privilege fingerprint on the exact target. `supabase/ci/production-validation.sql` checks relevant fence, lifecycle, gateway and session objects and privileges; `scripts/migration-checklist.ts` checks that the static SQL checklist covers all 83 files. Neither by itself runs a hosted check or proves file-level history on a target with duplicate version prefixes.

Netlify runs `npm run build` independently; the repository workflow is a local source/test gate and does not apply or verify the target database before deploying. Docker builds independently as well. **No automatic cross-platform migration-before-deploy guarantee exists.** The safe compatibility behavior is fail-closed: missing, unavailable or unknown protocol metadata returns 503, including for legacy, and never invokes the legacy paper RPC. The readiness endpoint checks that the protocol column is reachable using a zero-row query and returns degraded if it is not; this detects a common incompatibility without reading answers, but is not wired as a Netlify deploy gate and cannot establish that the fence, roles or migration history are correct. An operator must block rollout and traffic until the reviewed target-specific verification passes; an incompatible rollout can interrupt legacy CBT. Do not substitute an environment flag or infer v1 from missing metadata. No target was contacted in this audit.

## Paper response and question eligibility

The local guarded v2 branch verifies the caller through Express Auth and capability checks, then owner-filters both the attempt and stored protocol; any unknown protocol fails closed. It requires a nonempty, unique, valid ordered UUID array from that attempt, restricts questions to those IDs and that exam, excludes `review_status='rejected'`, and requires every frozen ID to resolve exactly once. No replacement or shortened paper is generated. The response projects only position, subject, question ID, question text and four options; the database query does not select correct answer, explanation, marks, provenance or administrative fields. Attempt metadata includes the student's own status, draft and exam metadata.

The existing planner selects from an active exam and excludes rejected questions at creation. Per `20261022090000_cbt_question_serving_rules.sql`, `needs_review` and `approved` questions are usable; `needs_review` is not a publication claim. There is no separate per-question publication flag here. Like the existing frozen legacy reader, the v2 reader does **not** require an exam bank to stay active after an attempt was frozen. The question update/delete guard prevents later ordinary edits/deletes to referenced v2 questions. Missing or rejected frozen questions fail closed instead of being replaced. `in_progress` and `expired` attempts can provide a paper; expired read access is for preserving local recovery, and the database session and answer gateways deny closed/expired writes. Cancelled/submitted/invalid lifecycle states cannot open the v2 paper. Neither a local status nor a paper authorizes writing or finalization.

A takeover that commits before a stale answer acquires the attempt lock must reject that answer. If an answer acquires the lock and commits first, that earlier accepted write is a valid serialization, not a stale write accepted after takeover. IndexedDB intent keeps its original operation and lease; resolving old work on a new session requires explicit review and a new operation. The server cannot discover offline work never registered by another device.

## Remaining decisions / restrictions

For the subsequent shared-bank reproduction and the migration-first operating procedure, see [the shared-bank investigation](CBT-SHARED-BANK-RELEASE-SAFETY-2026-11-07.md) and [the migration-first release procedure](../operations/CBT_MIGRATION_FIRST_RELEASE.md).

The code fails closed on missing protocol metadata but cannot make an independent Netlify or Docker deployment wait for a target migration. Before any app rollout, an authorized release owner must establish an enforced or otherwise independently approved migration-before-app release gate, verify the whole fence and target identity, and plan the legacy outage risk if that order fails. The local readiness check is not such a gate. The shared practice-bank correction behavior also needs an explicit product/security decision if answer-key confidentiality against other guests or legacy practice sessions is required. Do not misrepresent the safe v2 response as proof of bank-wide secrecy. These are not evidence of real Supabase validation and were not resolved by changing hosted resources or guest policy.
