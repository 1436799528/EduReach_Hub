## V2 server lifecycle update — local only

`supabase/migrations/20261107130000_cbt_v2_server_lifecycle.sql` extends the existing fence without rewriting its legacy RPCs. It adds `candidate_answer_revision`, a stored v2 result and an RLS-protected `cbt_v2_operations` ledger. `cbt_candidate_answer` and `cbt_candidate_finalize` are owned by `cbt_v2_executor`, executable only by the unassigned `cbt_v2_client` role, and check `auth.uid()`, expected identity, the authoritative attempt protocol and the row state. No ordinary role has been granted the v2 role. The page writer remains blocked and no hosted action was performed.

Each attempt-scoped operation ID binds to its complete input. Accepted answer/clear operations update the authoritative draft and revision under the attempt lock; duplicate requests replay, changed payloads under the same ID are refused, stale revisions produce a durable conflict and cannot overwrite later answers. Finalization takes the same lock, checks the expected revision and contiguous accepted-answer ledger, validates frozen paper/draft and scores only the stored draft. It stores answers and result atomically; repeated finalization returns the stored result. The v2 draft, operation history and result persist with the attempt until it is deleted; an approved retention/deletion policy is still required. Deadline and existing 120-second delivery grace are checked using wall-clock time after the lock. The ledger proves **server-accepted operations** only: it cannot detect another device's unregistered offline intent. A participant-registration/drain protocol or a separately approved product restriction is still required before claiming that no offline intent is silently omitted.

## Proposed durable state model

- Add a database-owned discriminator to `cbt_attempts`, with explicit `1` for existing/legacy attempts and `2` for newly created v2 attempts. A constant default of 1 preserves the semantics of old INSERTs; migration must demonstrate it changes no historical answers, deadlines, row lifecycle or policy. No persisted UNASSIGNED state is required: classification is assigned in the same transaction as insertion.
- Protocol is immutable after INSERT: **1→2 and 2→1 both rejected**, even for callers who control a JWT, HTTP header, query parameter, localStorage, session setting or expected protocol field. A future migration policy for existing attempts is not authorized. Authorized v2 creation inserts a fully initialized v2 attempt, including validated frozen question IDs and revision zero, without first exposing or converting a committed legacy row.
- The version value comes from the owned attempt row. A v2 RPC checks `protocol=2` under its lock, an old RPC refuses protocol 2, and a response includes that database-derived value. A client capability can determine whether to render/refuse, but never override the row, authorize DML or cause v2→v1 fallback.
- Attempt lifecycle is separate from protocol: `in_progress` may reach `submitted`, `cancelled` or `expired` under explicitly authorized version-specific transitions and existing timing. Closed/submitted states must not become active or be rescored. Deletion is a separately reviewed owner/admin operation, not an automatic downgrade. The final v2 transition/error semantics still require real definitions and tests.

## Start/resume contract and serialization design

1. Share the existing question validation and paper planner rather than create a divergent set of exam rules. Extract a side-effect-free paper preparation function or equivalent reviewed shared component. It must preserve question-count, subject, mode and timing outputs of the existing configured start. Do not invoke the current side-effecting legacy start as the v2 creator: it can cancel/resume a v1 attempt, including under a concurrent other-mode request.
2. All start/resume entry points, including direct old `start_cbt_attempt`, configured start, a new v2 creator and any still-executable aliases, must coordinate on the **same user/exam transaction lock** before deciding whether a row exists. Take locks in a documented order: shared user/exam lock, then attempt row `FOR UPDATE`, then dependent state; retain the unique active index as last defense. Any direct table INSERT/UPDATE path that can violate this invariant also needs authoritative database enforcement or explicit least-privilege treatment without breaking v1. Trigger/advisory lock interactions and deadlocks require real concurrent tests, not an assumption.
3. A v1 start must never return or cancel a v2 attempt, including same configuration or a different mode. It returns an explicit incompatible-protocol error. A v2 start must not create over, cancel, convert or return a v1 attempt as v2; it returns an explicit mismatch. Matching v1/v1 and v2/v2 resumes preserve their own behavior. A first successful creator atomically initializes paper, timing, protocol and identity; an incompatible concurrent creator waits and then fails without modifying the winner. A retried/lost response needs a separately designed creation-idempotency or unambiguous owner resume contract.
4. Preserve the existing v1 signatures, grants and semantics for v1. Minimal version-aware checks may need modifications of existing function definitions; they must not globally revoke or replace the legacy *behavior*. Real function definitions, exact lock-order changes, timestamps, error behavior and v1 compatibility need review and tests before migration creation. Old deployments and in-flight requests must be covered by database enforcement, not only a new server.

## Lifecycle and privilege design

The proposed boundary is a combination of version-aware RPC checks (including read-only resume) and a database row/lifecycle guard, **not** the candidate's global revocations. Protect attempt ID/owner/protocol, frozen paper, deadline, draft/revision, status/result and `cbt_answers` insert/update/delete; account/exam/question cascades, direct service DML, security-definer calls, alternate writers and correct delete/expiry paths need explicit treatment. V2 functions must authenticate `auth.uid()`, own the attempt and hold the appropriate row lock. V2→legacy calls fail at the DB and handler; no whole-snapshot RPC is used.

One candidate mechanism is a narrowly scoped NOLOGIN executor role owning only reviewed v2 `SECURITY DEFINER` functions, plus an **invoker-context** trigger that tests the effective database role, not a session-settable flag. It works only if the API authenticator, authenticated role, service role, other login roles and existing definers cannot assume or inherit that executor; public/default EXECUTE and schema/table/function privileges, ownership, `SET ROLE`, default privileges, definer search paths and trigger context must be checked in the **actual migrated catalog**. The migration runner needs sufficient rights to create/assign the role; verify managed hosting permissions in authorized staging. Trusted DB owner/superuser and DDL still can alter/disable a fence and need procedural controls. A role name or GUC alone is not a security proof. Account deletion and cascades must have a reviewed versioned path so the guard does not falsely claim deletion or globally break v1.

## Concurrency and quiescence

A complete server-side immutable version fence and shared lock can isolate old/new clients and simultaneous start/resume/lifecycle requests without a permanent global shutdown or waiting for every old client. In-flight legacy mutations either commit before v2 is created on a different attempt or are refused against an already-v2 row; no existing attempt is converted. Rollout may require a separately approved operational cutover/quiescence **only** where a deployed writer bypasses the fence, the database migration cannot install it atomically, or rollback cannot preserve the v2 path. Those cases need discovery and explicit cutover procedures, not an assumed permanent runtime requirement.

A distinct problem is **submission of offline local intent**: two worlds can have identical server revision and messages while a second device either has, or has not, saved an unsent local operation. A database fence cannot infer which world it is in. If the product requires an absolute guarantee that finalization never silently excludes any such intent, it needs a provable way to account for potential writers/intents (for example durable participant registration and drain/freeze), or must change the offline-capture/explicit-confirmation semantics. That is a finalization and product guarantee question, not proof that lifecycle protocol isolation itself requires permanent global quiescence. The earlier owner chose strict participant protection; its precise protocol and its availability impact are unproven and remain a submission dependency, not a prerequisite asserted for merely distinguishing v1/v2 attempts.

## Earlier additive migration and rollback design — pre-implementation

1. Inventory actual effective writers and role membership. In a new migration add durable version metadata defaulting existing and old-inserted rows to v1 without changing records, plus targeted v2 metadata. Preserve the existing active index and v1 grants. Do not put the incompatible candidate into migrations.
2. Install a per-attempt immutable-version and lifecycle/answer guard plus owner-scoped v2 read/start/lifecycle functions. Refactor a **shared** pure paper planner and version-aware checks into actual legacy and v2 start paths, maintaining v1 behavior. Establish locks and consistent v1/v2 result/error contracts. All this is an intended design, not a present function signature or verified privilege model.
3. Verify the migration against real disposable PostgreSQL with old attempts inserted **before** migration; compare old records/grants and exercise all direct, legacy, service/role and security-definer paths, owner isolation, lifecycle/cascade behavior and concurrent starts. Only after this gate can the real page writer be considered. No hosted migration is authorized.
4. Roll back operationally by disabling **new v2 creation**, retaining discriminator, all fences, data, read/compatible lifecycle APIs and v2-capable clients while attempts remain; otherwise keep v2 read-only for controlled recovery. Rolling an old server/database back across the fence can expose v2 to legacy paths. Schema/data removal requires separate reviewed drain, backups and rollback authorization; never downgrade attempts in place.
