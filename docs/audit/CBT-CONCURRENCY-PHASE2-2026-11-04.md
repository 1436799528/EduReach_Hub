## Schema, live metadata and compatibility

- Read-only production metadata inspection found RLS enabled with only authenticated SELECT policies for `cbt_attempts` and `cbt_answers`; anon/authenticated lack direct INSERT/UPDATE/DELETE grants. Service role has all three write privileges on both tables. The only non-internal CBT-table trigger listed is the subject-combination trigger; there is no revision guard. Relevant public RPCs are owned by `postgres`, generally SECURITY DEFINER.
- A read-only aggregate at audit time found one cancelled and five submitted attempts, none with a nonempty draft, and no in-progress row. This is a point-in-time count, not authorization to mutate or proof there will be no active attempt at rollout. No user identifiers or answer content were retrieved.
- The candidate adds a revision column to the existing attempt row and an operation ledger; it does not create a parallel answer store. It currently changes known legacy RPC permissions, renames the existing scorer, revokes service-role DML and supplies an inaccessible old-signature stub. **It is intentionally incompatible with today’s application and older clients**; it is not placed in `supabase/migrations`.
- A deployable migration requires independently reviewed effective privileges, dependencies, function owners/default privileges, all privileged writers, existing-attempt backfill and safe handling of unknown clients. Service-role revocation conflicts with the existing expiry updater. Postgres owner/superuser can still bypass candidate rules; permissions alone cannot constrain that role.
- A coordinated client/server/database cutover must refuse or safely version-gate old writers, preserve in-flight attempts and accepted drafts, and avoid an unsafe rolling-upgrade window. Rollback must not reinstate snapshot writes over newer accepted drafts. A maintenance/cutover and compatibility plan has not been approved or verified.

## Phase 2 isolated work

- `supabase/candidates/cbt_revision_protocol.sql`: after row-lock acquisition, candidate writes check `clock_timestamp()` against the same deadline, and candidate finalization checks the existing `cbt_submit_grace()` against actual time. Neither time value was changed. Private scorer and known legacy/service-role permission rehearsal were added. This does not protect the active app.
- `src/lib/cbtReconciliation.ts`: pure, unwired three-way comparison. A known base allows local-only differences to be represented as **unsaved proposals**; incompatible edits/clears require explicit review. Missing base makes every mismatch a conflict. It never sends or marks answers saved. It must not be treated as an authoritative transport or UI implementation.
- `tests/cbt-authoritative-candidate.test.ts`, `tests/cbt-reconciliation.test.ts`, `scripts/rehearse-cbt-candidate-races.mjs`: isolated regression coverage, including known legacy permissions and lock waits across deadline and grace. A red PostgreSQL test first reproduced post-deadline acceptance using `now()` before the fix.
