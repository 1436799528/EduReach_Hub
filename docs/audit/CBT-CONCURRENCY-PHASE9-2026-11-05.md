## Canonical rule and local compatibility strategy

Valid account, attempt, question and operation UUIDs are represented as lowercase strings. New `add`/enqueue operations and conflict replacements are canonicalized, compound-scope queries normalize their inputs, transition/retry/resolve normalize operation references, and the queue stores a canonical scope for the Web Lock and local transport. This changes spelling, not the UUID value or the operation's logical identity. The isolated candidate's SQL accepts `uuid` parameters and stores the operation and question as PostgreSQL UUIDs; that local SQL behavior does not prove any hosted backend behavior. Frozen non-identifier payload fields remain unchanged.

Opening the local database requests IndexedDB **version 2**. A fresh database creates the same stores and scope index; a version-1 database is upgraded in one IndexedDB versionchange transaction. It validates every old row, lowercases the four UUID fields, checks collisions and sequencing, preserves the existing counter, clears and repopulates the existing operations store within that same transaction, and lets IndexedDB rebuild the existing index. A bad row, divergent operation-key collision, distinct operations with the same sequence, or a counter behind the rows aborts the whole transaction; the old version and rows remain intact. These checks deliberately fail closed for questionable data rather than deciding which answer is authoritative. Rows in other accounts are also checked during upgrade, so a corrupt unrelated row can block the local database until reviewed. This is a browser-local schema upgrade, not a hosted or production-data migration.

If case variants normalize to the same global operation key, a duplicate is collapsed only when all cloned own fields match exactly after UUID normalization and contain no object-valued fields; otherwise the entire upgrade aborts. Distinct IDs stay distinct even for the same account, attempt and question. Existing `add` semantics reject a duplicate primary key rather than treating it as a successful replay; the rejected transaction does not increment the committed counter. This avoids silently creating a second row or replacing a different payload. An old tab holding version 1 can block the upgrade; the failed open reports storage unavailable, and if that old tab later closes the already-failed upgrade is aborted rather than executing in the background. New connections close on `versionchange`; a subsequent explicit retry can upgrade. Other tabs and notifications are not authority for server answers.

Operational limitations: migration scans and rewrites the whole local operations store, so large/corrupt journals, storage quota failures or unsupported IndexedDB can fail closed. Conflicting records require a future reviewed recovery path; no automatic destructive repair is provided. Old version-1 code cannot open the upgraded database with its old version. The current UI still blocks v2; no cutover or old-client coexistence safety is claimed.
