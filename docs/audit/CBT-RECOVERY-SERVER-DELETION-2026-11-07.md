## Device policy and release gate

The following is a required design, **not implemented or approved**:

1. A v2 writer must be registered with the server before it may persist or send an intent. Bind a server-issued, unguessable session/device identity to the authenticated user and attempt. Server-side revocation, not a browser assertion, determines validity. Define registration limits and how browser storage loss is handled.
2. Submission must atomically enter a server-side closing phase that prevents new sessions/intents; all active registered devices must freeze local writes, recover, and provide server-validated durable checkpoints covering their known operations. The submitting device's local seal is necessary but insufficient. A disconnected device with an unverified checkpoint blocks submission unless an explicitly approved conflict/loss policy is applied; never silently retire it.
3. Registration cannot reveal intents created by unregistered/offline clients. Therefore every client capable of creating v2 intents must enforce prior registration; old or unknown clients must not be allowed to create them. Existing unsupported or unregistered local intent cannot be declared absent.
4. A retired or old device reconnecting after submission must receive an explicit closed/conflict outcome, retain and expose any unsent local intent for review, and must not overwrite the result. Replayed accepted operation IDs must remain distinguishable from new unseen operations. Device retirement and exception handling need an approved procedure and audit trail.
5. Coordinate this policy with the existing deadline and 120-second submit grace; do not silently extend either. How to resolve a device that remains offline through expiry is an unresolved product policy decision, not permission to discard intent.

The persisted local seal intentionally has no automatic unseal. Unknown finalization response, conflict, local storage loss, account changes, abandoned or superseded histories, and migration between devices need a reviewed, recoverable protocol before any UI integration. A local seal alone must never be interpreted as a complete submission barrier.

## Deletion evidence and decisions

The local SQL rehearsal applies all 81 migrations to a private-socket disposable PostgreSQL instance. In synthetic fixtures, a raw `DELETE` on `auth.users` for a user with an active legacy attempt cascades that attempt; this demonstrates an existing bypass of any future controlled lifecycle. For an active v2 attempt containing one accepted operation, two raw Auth-table delete attempts both fail at the protocol fence and leave the user, attempt and ledger intact. Deleting that v2 attempt through its restricted transition and then deleting the synthetic user succeeds. **This is a narrow DB observation, not a controlled account-deletion workflow, policy approval, real Auth API integration, partial-failure workflow test, or proof of erasure.**

Decisions still required include eligibility/recent authentication and confirmation, handling active v1/v2 exams and offline intents, audit integrity and the last administrator, per-category deletion/retention/de-identification, cross-user content and storage ownership, exceptions and administrative review, indirect identifiers, backups/processors and restore replay. Do not invent periods, legal grounds or promises. A future workflow must persist its progress, prevent raw Auth bypass within the relevant trusted application/Auth boundary, survive failures between database, Auth and Storage, and only report completion when approved steps are verified. Qualified Nigerian legal and product/security review remain release blockers.
