## Negotiation, local-only gate and compatibility

The server includes exactly `{version: 1}` on the normal paper response, or `{version: 2, scope: 'local-rehearsal'}` when `CBT_V2_LOCAL_REHEARSAL=1`, `NODE_ENV` is not production, `NETLIFY` is unset/empty, and `VITE_SUPABASE_URL` is HTTP on `localhost` or `127.0.0.1`. The same server-side gate guards v2 endpoints. No browser environment variable is accepted as proof. The actual session rejects the v2 marker deliberately and displays an explicit inability to confirm answers; it does not fall back to v1. Missing/malformed/unknown metadata is rejected before paper state or pending answers are loaded. A generation counter ignores out-of-order paper responses; legacy write callbacks are blocked while negotiating and after failure. This is a safety interlock, not v2 capability to use the session.

The gate does **not** prove loopback is disposable: a local proxy could forward to hosted data. Operators must verify the target independently and never forward rehearsal operations to hosted data. A client receiving v2 from any server remains blocked, but the explicit local-only mode is not proof that old clients or direct writers cannot bypass the protocol. Existing server implementations without this metadata will cause the new client to refuse the paper, by design. Server-first coordinated rollout, old-client handling, caches and active attempts need a reviewed plan; nothing here authorizes deployment. In-flight requests already sent under v1 cannot be undone by this guard.

## Unimplemented requirements and why the guard remains

The candidate has **attempt-wide** revisions. A replay returns the operation's accepted revision together with the **current** draft, which can contain a later edit; it is not proof that the current local intent was saved. Conflicts are stored against operation keys, so reusing a conflicting key cannot resolve the conflict; a network-uncertain retry must instead preserve the original key and frozen payload. Whole localStorage snapshots have neither an authoritative base nor atomic compare-and-swap across tabs. Building a queue without addressing these cases can silently overwrite an answer or erase an unsent proposal.

Required but not implemented: account-and-attempt-scoped durable immutable operations and acknowledged base/revision, safe recovery after refresh/tab close/lost response/storage failure, protection from stale ACKs and newer local choices, authoritative fetch and explicit accept-server/resubmit-local conflict choices, multi-tab coordination with BroadcastChannel/storage only as hints, handling independent and same-question collisions, and review of old unversioned pending copies. Real v2 selection/clear/navigation/progress, online/visibility/lifecycle callbacks, manual and timer submission, draining/blocking pending or unknown operations, same-key finalize retry and server-draft results navigation are also absent. There is no proof of v2 offline/reconnect, multiple pending, deadline/grace, delayed-browser, duplicate/lost-finalization, unavailable-backend, storage-failure or two-session edit behavior. The initial block neither submits nor scores an attempt; time can continue to run on the server, so it must not be used for a real examination.

## Rollback, next steps and readiness

Do not enable `CBT_V2_LOCAL_REHEARSAL` against real data or enable the candidate on hosted databases. Do not use a v2-to-v1 fallback, revoke legacy permissions early, alter the grace period, or discard old pending snapshots. Reverting client/server changes independently could make metadata negotiation incompatible; coordinate any eventual rollback and preserve already accepted answers and unconfirmed local proposals. A validated forward-only data recovery and active-exam strategy is still required.

Next: implement and test the durable queue and explicit reconciliation inside the actual session; test two real UI pages against actual HTTP plus disposable PostgreSQL across the requested failures and deadline/grace cases; review a real deployable migration and exhaustive old/privileged writer fence; run full CI and authoritative GitHub checks, then isolated staging cutover/rollback and real Auth/RLS tests. The owner need not supply production credentials or run migrations. When staging is restored, authorized staging verification and review are needed; legal, privacy, deletion, service and news blockers in the broader launch audits remain open. Overall status remains **NOT READY**.
