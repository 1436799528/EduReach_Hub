# Shared-bank answer disclosure investigation

## Finding and classification

**Demonstrated exposure of shared practice-bank answers; not a v2 paper-response leak or a v2 write/finalization bypass.** `POST /api/cbt/guest-submit` intentionally returns a correct option and explanation for each guest paper position for which the caller supplies any valid answer, including a wrong answer. The caller can submit all positions. If those same records are frozen in a v2 attempt, this exposes their answers independently of that attempt's owner, writing session and lifecycle. A person can do this while a v2 attempt is active or before a future attempt starts, whenever the bank is active and the relevant questions are available in the guest paper. Rate limits constrain requests; they are not an authorization or secrecy boundary.

The direct v2 paper response is still owner-scoped and its question projection contains no correct option/explanation. Both statements are true. **Do not represent this product as providing answer secrecy for shared practice questions against guests.** Guest practice corrections remain available. Confidential examinations must use a restricted question bank whose questions and answer keys cannot be reached through public guest-scoring endpoints or other unauthorized answer-bearing paths; the separation must be enforced and tested at the authoritative boundary before those examinations are offered. That separation is not implemented or verified here, so confidential high-stakes CBT is **not ready**. V2 creation and public finalization remain disabled; this investigation makes no deployment or hosted-readiness claim.

## Code trace

- The v2 start path `supabase/migrations/20261107120000_cbt_attempt_protocol_fence.sql` calls the configured planner; `20261022090000_cbt_question_serving_rules.sql` selects IDs from `public.exam_questions` by `exam_id` and subject and excludes rejected questions. The attempt stores ordered `question_ids`. In `server.ts`, `GET /api/cbt/attempts/:attemptId/paper` authenticates the user and owner-filters the stored attempt, then reads those same IDs from `exam_questions`, selecting only subject, question text and four options.
- `server.ts` `GET /api/cbt/exams/:examId/guest-questions` and `POST /api/cbt/guest-submit` require an active `cbt_exams` row. `fetchGuestBankQuestions` reads `exam_questions` by the **same exam ID** and excludes rejected rows. `selectCbtPaperQuestions` chooses at most 100 eligible rows using the supplied subjects and caller-controlled seed; display and scoring rebuild the paper using the same seed. A guest can choose the paper/seed and repeat subject to rate limits; one request is not guaranteed to include every row of a larger bank. Guest display reports paper positions, not the DB question UUID.
- Guest submit does **not** accept arbitrary UUIDs as direct question lookup. Its `answers` object is keyed by the reconstructed 1-based paper position. Extra UUID keys are ignored. An absent/null position does not receive `correct_option` or `explanation`; integer choices 0–3 do, whether correct or wrong. The response includes question UUIDs, text/options and attempted-question corrections, making the overlap matchable. A complete valid answer sheet returns all corrections for that reconstructed guest paper.
- There is no guest authentication, attempt ID, ownership check, v2 session or attempt-status check. The service-role backend query can read keys; guests cannot directly SELECT `exam_questions` through the intended database grants. `guestCbtSubmit` has an in-process and durable IP bucket of 30 per 600 seconds; durable failure falls back to the in-process limiter. The limits make bulk retrieval harder, but a single request can reveal an entire guest paper and they do not prove secrecy.
- Deactivated banks are not guest-scored or served, but frozen v2 and legacy papers remain readable after deactivation. Previously retrieved answers are not made secret again. There is no question-level published/private flag in this design, and `needs_review` is usable under established rules.
- This correction contract is deliberate: `tests/guest-cbt-disclosure.test.ts` explicitly tests that only attempted questions receive corrections and that a fully attempted paper receives the complete key; its comments describe a review-screen need. `STAGING_VERIFICATION_RUNBOOK.md` also specifies per-attempted-position correction. The current source search did not establish an in-tree UI caller of these exact guest endpoints, so the reach of existing consumers needs verification. Preserve the documented API behavior unless the owner explicitly changes the practice policy.

## Local evidence and limits

`scripts/rehearse-cbt-http-boundary.mjs` applies all 83 migrations to a private disposable PostgreSQL instance and exercises actual Express handlers through a local synthetic Auth/PostgREST adapter. With a synthetic active exam and six synthetic questions, an unauthenticated guest submits six **wrong** choices and receives six correct answers. The test matches the returned database question UUIDs to all five frozen IDs of an already-active protected v2 attempt. It then starts a second v2 attempt and matches that future paper to the previously disclosed keys. It also asserts the guest paper has no key, empty/UUID-keyed guest answers do not reveal corrections, a single attempted position reveals only its correction, and deactivated banks are not guest-scored while frozen papers still load. This demonstrates the local code/data path, not a live hosted finding or a guarantee that every larger bank/paper overlaps in every case. The adapter is not real PostgREST/Auth.

## Narrow correction proposal — not implemented

For a use case that actually requires pre/during-attempt key secrecy, the narrowest effective control is an explicitly approved **bank-level access policy established before any questions are disclosed**: use banks whose answer-bearing guest correction and other legacy/result paths cannot be accessed by candidates before or during the protected use, and prevent protected attempts from selecting publicly corrected records. Apply and verify that rule at the authoritative server/database boundary for both creation and all answer-bearing readers. This requires an owner-approved way to distinguish eligible banks; do not invent a publication flag or assume `needs_review`, active status, or a browser toggle provides that distinction. Existing already-disclosed answers cannot be made secret by a new rule.

Simply withholding guest corrections for questions referenced by *currently* active attempts would alter guest practice while offering no protection for keys retrieved before attempt creation, previously closed/protected attempts, other answer-bearing legacy results, or race conditions. Blocking all guest corrections is broader and would break the documented guest API contract and any review consumer relying on it. A proper restricted-bank decision would deny or withhold corrections only for approved restricted banks and leave ordinary public practice intact, but must also prevent legacy/result routes from exposing those restricted keys. No such behavioral change is authorized or made here.
