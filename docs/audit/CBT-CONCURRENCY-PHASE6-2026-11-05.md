## Queue architecture and persistence

`CbtAnswerQueue` and `IndexedDbAnswerJournal` are standalone and not imported by the session. Each record includes account ID, attempt ID, question ID and position, local selection (including clear/null), base answer and expected attempt revision, immutable UUID operation key, created/updated timestamps, pending/acknowledged/conflicted/resolved-server/superseded/closed state, last server answer and revision, and accepted revision. An IndexedDB transaction assigns a monotonic local sequence, so ordering does not rely on wall-clock time; this is browser ordering, **not** server authority.

A new operation is committed to IndexedDB before it is returned and may be transmitted. Distinct changes receive distinct keys; prior requests are never updated under the same key. Journal transition checks preserve frozen request fields. Conflict supersession and insertion of a newly keyed resolution are one IndexedDB transaction, with rollback if insertion fails. No rows are compacted or automatically deleted. IDs and stored fields receive basic shape/scope validation. Actual storage contents are not trustworthy proof of server state; browser storage can be unavailable, corrupted, evicted or cleared, and contains sensitive answers. Retention, quota, lifecycle and cleanup policy remain unresolved.

The abstraction requires an account/attempt-scoped Web Lock before sends or resolution. If Web Locks are unavailable, sending fails closed; there is no unsafe localStorage lease fallback. It does not yet provide a time-bounded wait, queue-drain scheduler, BroadcastChannel/storage-event notification, or automatic recovery orchestrator. IndexedDB operations can fail; callers must display that failure and must not claim durable recovery. No real page currently displays queue-specific persistence, saving, retrying or conflict status.

## Idempotency, revisions and conflicts

`retry` reads the persisted operation and sends exactly its original question, selection, expected revision and operation key. Network errors leave it pending. For a confirmed acceptance/replay, it checks the accepted revision against `expectedRevision + 1`, requires a valid current server revision/draft, and records acknowledgement only if the **current** server answer still matches the operation. A replay that was accepted earlier but now has a different server answer becomes a conflict instead of a false current-save claim. Later operations are separate records and are not cleared by an older response.

On a conflict, the journal first persists conflict state and the reported server answer/revision, then fetches authoritative state. If that fetch fails the original local proposal and consumed conflict key remain recorded. Resolution requires an explicit `server` or `local` choice plus the revision and answer that were reviewed. It fetches current state again; if the reviewed state changed, the conflict is updated and another review is required. Choosing server records that choice without deleting the local proposal; choosing local atomically supersedes the old conflict and creates a new UUID operation against the reviewed current server revision. It does not send that new operation until the caller explicitly retries it.

These APIs still require safe mapping between the server's frozen paper question IDs and positions, authenticated account change handling, authoritative snapshot refresh/projection, old pending-snapshot handling, and per-question UI conflict controls. The queue does not itself know whether a caller-supplied base answer was actually acknowledged by the server. It must not be connected to a real session until the caller establishes and maintains that invariant. Global attempt revisions mean even independent-question races currently need explicit resolution in this isolated implementation.

## Multi-tab coordination and refresh

The IDB journal is origin-shared and scoped by account/attempt; Web Locks serialize the journal's cooperative dispatch/resolution in browsers supporting it. The database candidate, not the lock or local journal, is authoritative. A second page can list and explicitly retry a pending operation after the first page closes. The implementation **does not notify** an active tab when another tab commits, fetch authoritative state automatically on notifications, reconcile the visible page, or retry automatically after reconnect. It therefore does not satisfy the requested multi-tab session behavior. Different devices and browsers do not share the journal. Existing old clients and privileged writers can bypass the candidate.

On reopening the journal, pending operations retain their keys and frozen payloads. This has been tested with an injected server and real browser IDB; it is not proof of real CBT page recovery. LocalStorage's old unversioned attempt snapshot must not be silently imported or overwritten because it has no trustworthy base. None of this is an offline exam capability.

## Actual page integration and transport separation

No Phase 6 edits were made to `pages/CbtSessionPage.tsx`, its styling, the v2 endpoint gate or the database. The Phase 5 v2 guard and v1-only legacy callback guards are intact. Missing, malformed and advertised v2 paper metadata still fail closed in the actual page, so no v2 answer or submit route can fall back through that page to the legacy snapshot writer. The session cannot currently answer, synchronize or finalize a v2 paper. A previously dispatched legacy request cannot be recalled; older deployed clients and direct RPC/privileged writers remain outside this protection. A loopback URL can proxy hosted data and is not proof of disposal.

The work deliberately stopped short of connecting the journal because automatic dispatch and tab synchronization could otherwise display a stale answer as current, mishandle unknown bases or account changes, or leave a student with a running exam and no safe submission. Those missing requirements are not represented as completed integration.
