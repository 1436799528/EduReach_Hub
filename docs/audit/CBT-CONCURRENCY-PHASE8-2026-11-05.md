## Performance investigation

The baseline was a clean completed `npm run build`, before browser tests: **344,212 bytes gzip**, or **336.1 KiB**, across all JavaScript chunks; the unchanged limit is **344,064 bytes (336.0 KiB)**. The page statically imports `inspectCbtAnswerJournal` and `validateCbtJournalPaper` from the shared journal module. The production Vite/Rollup graph included `cbtAnswerQueue.ts` in the lazy CBT session chunk and `cbtProtocolValidation.ts` in the shared entry chunk. `fake-indexeddb` was absent from that graph. Production output contains the journal-review error used by the reader but not distinctive writer/queue-lock strings, consistent with the unused class/writer being tree-shaken; this is not a claim that every unneeded byte can be identified by string matching.

A **non-writing, in-memory counterfactual build only**, replacing the page's preflight imports with no-op stubs, measured **342,943 bytes**, versus the final real build's **343,800 bytes**. The net **857-byte** difference includes removing the preflight reader/validator and adding the temporary stubs; shared validation and chunk compression mean it is not an isolated module-size figure. The stubs were never saved or shipped, and removing validation is not an acceptable optimization.

Measured attempts: a repeated-field `.every` consolidation worsened gzip to 344,219 bytes and was reverted; a one-pass Terser build was 345,885 bytes and reverted; a modern-output setting made no measurable improvement; a numeric-cast rewrite and shared object-shape guard worsened output and were reverted. The equivalent compact UUID expression, shared answer validator and one paper lookup reduced the two-pass build to **344,159 bytes**, still over budget. Standard Terser `hoist_funs` subsequently reduced the final real build to **343,800 bytes / 344,064** (**335.7 / 336.0 KiB**), a **412-byte** improvement over the initial baseline, with **264 bytes headroom**. `booleans_as_integers` was examined but not enabled because it can change strict boolean semantics. No budget was increased and no check was disabled. Full PERF-1 audit: **10/10 passed**, entry 97.7/100 KiB, CSS 50.9/51 KiB, critical path 206.8/211 KiB. This narrow headroom is not sufficient evidence that a full integration will fit.

## Concrete safety blocker and integration gap

A disposable `fake-indexeddb` experiment inserted one pending operation using lowercase account and attempt UUIDs. Listing with the exact lowercase scope returned **1**; listing with the same two UUIDs in uppercase returned **0**. IndexedDB's compound scope index is string-case-sensitive, and the attempt URL can differ in casing. That can hide pending intent during recovery. Merely normalizing newly created scopes is insufficient because differently cased records may already exist. A correct repair must find or safely migrate existing variants transactionally, preserve identities and order, avoid account leakage, handle concurrent tabs and canonicalize lock identity, with tested failure/rollback and no lost pending work. No such repair is claimed here.

Other prerequisites remain: authoritative snapshot/revision plus the existing sole `answers` projection; transactional operation creation before send; preserving immediate local intent across an earlier acknowledgement; strict same-question scheduling without silently changing immutable in-flight identities; same-key retry after unknown commit; explicit conflict resolution with a fresh identity; accurate unsaved/conflicted/storage-failure UI; account/session changes; storage failure and eviction handling; advisory cross-tab notifications followed by authoritative fetch/reconciliation; online/reload recovery; and safe navigation without legacy snapshot writes. The queue's existing operation base and revision semantics need end-to-end orchestration rather than simply wiring `choose` to `enqueue`. Web Locks are coordination rather than server authority. LocalStorage snapshots cannot supply a trustworthy v2 base.

**Required actual-page evidence still missing:** two real session pages editing the same question with visible local/server conflict and explicit resolution/operation IDs/final server value; independent-question survival; pending refresh; commit with lost response and same-key replay; offline/online recovery; navigation without inventing operations; and proof of no legacy answer/progress/RPC writer during v2 editing. The existing two-page session test proves only that both pages remain blocked and do not fall back; the separate isolated journal harness and raw HTTP race are not these tests. V2 submission remains intentionally blocked.
