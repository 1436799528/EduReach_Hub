## What was implemented

- `server.ts` provides local-only state, per-question answer and finalize HTTP endpoints. They require protocol 2, validate operation keys/revisions/answers, resolve the caller, use a user-scoped RPC client without service-role fallback, and preserve explicit 409 conflict/expired/closed outcomes. Database candidate checks owner, frozen question, revision and post-lock deadline, locks the row and atomically records operation identities. Candidate finalization scores its accepted server draft through the existing scorer.
- The gate requires `CBT_V2_LOCAL_REHEARSAL=1`, non-production, non-Netlify, and a loopback HTTP Supabase URL. This prevents an obvious hosted URL but **does not prove the loopback service is disposable** (a proxy could forward elsewhere). Operators must still verify target identity; never point it at hosted data. `CBT_V2_TEST_IMPORT` suppresses automatic server startup only in this local test mode so the test harness can bind its own listener.
- `src/lib/api.ts` adds transport helpers for the local v2 endpoints and checks response shapes, preserving conflict data rather than treating a 409 as a successful save. **The actual session does not call these helpers.** No frontend queue, conflict UI, multi-tab synchronization or v2 manual/automatic submission was implemented.
- `scripts/rehearse-cbt-v2-http.mjs` starts isolated PostgreSQL, applies 79 repository migrations plus the deliberately incompatible candidate, runs the actual Express handlers through a synthetic Auth/PostgREST bridge and cleans up. With the temporary Chromium executable it also races two real browser pages issuing HTTP requests. It does not run the CBT session interface or actual Supabase Auth/PostgREST/RLS.

## Local evidence and limits

- `tests/cbt-v2-client.test.ts` and `tests/authorization.test.ts`: **29/29 passed**; v2 gate, input validation, caller-bound forwarding, no service fallback, conflict shape and malformed-acknowledgement rejection. These use HTTP stubs.
- Disposable PostgreSQL + actual Express handlers + synthetic bridge: owner isolation, accepted answer, stale conflict, lost-response-style retry after newer accepted answer, accepted-draft finalization, duplicate finalization and closed-attempt rejection passed. Two Chromium pages concurrently writing through real HTTP and PostgreSQL produced one acceptance and one conflict. This is **not** multi-tab reconciliation in the session UI; the tabs sent requests directly.
- Existing Phase 3 real PostgreSQL concurrency tests exercise candidate lock waits across deadline and 120-second grace. They are not end-to-end timer/UI evidence. Existing synthetic compatibility test for the additive expiry migration preserves active, empty, malformed-object, expired and submitted rows; it does not migrate them into v2. Null drafts are disallowed by the local replay schema. Old pending/offline browser snapshots have no trusted base and cannot be auto-imported safely.
- Full local `npm run ci` stopped at the Node tests: **816 passed / 1 failed** out of 817. `tests/schema.test.ts` correctly reported `cbt_candidate_answer` and `cbt_candidate_finalize` are referenced by application code but not created by deployable migrations. The check was **not weakened** and no dummy migration was added. Later CI stages did not run. A separate build and performance audit passed **10/10**, including **334.5/336 KB** gzip. Historical Phase 3 CI results do not validate phase 4 changes.

## Cutover and rollback blockers

The Phase 3 drained-cutover design has not been demonstrated. There is no integrated versioned queue, trustworthy multi-tab reconciliation, actual UI conflict resolution, persisted per-operation retry across reload, timer/manual submission workflow, local integrated browser session, version gate for legacy endpoints, safe legacy/privileged writer fence, full integration migration or v2 rollback rehearsal. Candidate SQL remains outside deployable migrations and deliberately breaks old clients. Do not enable the candidate on hosted databases, revoke old writers, revert to unsafe snapshot writers after v2, or claim accepted local/offline edits were persisted. Unknown external privileged writers and operation-ledger retention/abuse policy also block approval.
