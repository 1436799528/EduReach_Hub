# CBT answer execution boundary — local design

This is a local-only implementation/rehearsal, not a rollout authorization. The page writer and v2 creation remain disabled. Finalization must remain unavailable until a server-enforced registered-device recovery barrier exists.

## Alternatives reviewed

| Option | Caller identity / execution role / owner | Effective access and RLS | Impersonation and direct invocation | Finalization risk |
| --- | --- | --- | --- | --- |
| A. Generic SECURITY DEFINER wrapper | Supabase bearer `auth.uid()`; wrapper owner determines database execution identity. | A wrapper owned by the existing `cbt_v2_client` could execute both answer and finalize, even if its code currently exposes one. RLS follows the function owner; an unrestricted owner widens its impact. | A wrapper taking a user ID can impersonate unless it independently binds it to `auth.uid()`. If granted to authenticated it is directly callable as an RPC. | An owner that can finalize or a generic operation selector risks exposing submission without recovery. Reject generic wrapper. |
| B. Trusted server DB login | Express verifies token; server uses a distinct login and supplies identity. Function executes as its definer. | Requires a new server-only database credential, network/pooler support, least-privilege connection role and transaction-scoped cleanup of identity. RLS follows chosen roles. | The trusted login can generally forge request-identity GUCs if it can connect; credential compromise and pool identity leakage matter. Direct RPC depends on grants. | Separate finalizer grants would still need a database-enforced recovery barrier. Not selected because the existing user-scoped Supabase route can satisfy answer-only identity binding without another credential. |
| C. PostgREST-accessible answer-only wrapper | Original verified user token is forwarded; PostgREST supplies `auth.uid()`. A new NOLOGIN answer gateway role owns only the wrapper and can execute only the internal answer RPC. The internal SECURITY DEFINER RPC remains owned by `cbt_v2_executor`. | Wrapper has no table access and no finalization/start/transition privileges. Inner RPC executes with executor RLS policies and checks ownership, protocol, state, revision and operation identity. Only the wrapper is executable by `authenticated`; anon/service are denied. Internal RPCs remain restricted. | The wrapper has no user parameter: it binds expected user to `auth.uid()`. Direct RPC calls to the narrow wrapper are possible for authenticated users, so all security checks are in the database, not merely Express. PostgREST must verify JWTs and prevent untrusted users from selecting roles/GUCs; hosted behavior and role graph remain unverified. Database owners and a compromised trusted PostgREST login are outside this boundary. | Wrapper cannot call finalization. Finalization HTTP remains closed even for eligible-looking browser requests; internal finalize is not granted to the gateway. |

C is selected for an answer-only implementation. Its narrow authenticated EXECUTE grant is not a grant of internal RPC or general v2 access. It does allow direct answer submissions without the app's HTTP capability check; this is safe only if the token is a verified authenticated user, database ownership/protocol checks are enforced, and direct answer access for an owner is an accepted product policy. No server-side device registration has been implemented; operations still cannot establish whether another device has undiscovered offline intent. Do not expose finalization or integrate the page writer on this basis.

## Deletion guard review

`supabase/candidates/cbt_active_attempt_auth_deletion_guard.sql` remains a proposal, not a migration. Local real PostgreSQL tests demonstrated refusal for active legacy/v2 attempts and one concurrent foreign-key insert/delete ordering. Its definer must bypass or satisfy attempt RLS. Hosted ownership/permissions to install a trigger on managed `auth.users`, compatibility with Supabase Auth deletion and transaction behavior remain unverified. A stale `in_progress` attempt can block deletion indefinitely until an approved controlled lifecycle resolves it; there is no approved exception or retention workflow. Do not install it until those decisions and real Supabase compatibility are established.

## Implementation and local verification

- Migration `20261107140000_cbt_v2_answer_gateway.sql` creates a NOLOGIN, NOINHERIT `cbt_v2_answer_gateway` role and an answer-only SECURITY DEFINER RPC owned by that role. The role is granted `auth.uid()` and the existing internal answer function, not direct attempt or ledger access, start, transition or finalize. The wrapper has no expected-user argument. `authenticated` can execute the wrapper; `anon`, `service_role` and PUBLIC cannot. Existing internal RPC grants are not broadened to ordinary roles.
- The actual Express local-rehearsal handler verifies the token through `requireUser`, forwards the same bearer token through the existing user-scoped Supabase client, and invokes the wrapper. The actual v2 paper/state and lifecycle remain otherwise incomplete; this handler remains **local-rehearsal-only**, not a production rollout. The local finalization HTTP route authenticates but returns unavailable regardless of a claimed recovery flag. Existing `cbt_v2_client` still has internal finalization privilege; the actual migration grants it to no runtime login. Do not grant that role while the barrier is absent. The SQL race test grants it only to a disposable test login to model a privileged competing finalizer.
- An authoritative finalization barrier requires server-issued device/session registration before intent creation, closing that prevents new writes/sessions, verified durable checkpoints from every registered device, explicit handling of offline devices and old reconnects, and an approved expiry/conflict policy. A local IndexedDB seal alone cannot establish these facts. None is implemented here.
- Exact command:

  `env -i PATH="$PATH" HOME="$HOME" node --import tsx scripts/rehearse-cbt-http-boundary.mjs /tmp/cbt-reconstruction-tools/node_modules/embedded-postgres/dist/index.js`

  The real imported Express app and handlers issue HTTP to a loopback **synthetic Auth and PostgREST compatibility gateway**. The gateway validates local HMAC-signed test tokens, binds the subject to a non-superuser database session, and executes each profile/state/RPC response against real disposable PostgreSQL after all 82 migrations. CBT answer/conflict/ownership responses and SQL privilege decisions are not mocked. This verifies the actual app handler against real PostgreSQL through a deliberately limited compatibility layer, **not** actual Supabase Auth or actual PostgREST. It tests valid and invalid/expired/forged tokens, wrong ownership, legacy/v2 mismatch in both directions, direct internal-RPC and gateway-role denials, direct-wrapper impersonation, idempotent replay, stale conflicts, expiry, rejected HTTP finalization and a real locked answer-versus-privileged-finalization race.
- Local role/rollback command:

  `env -i PATH="$PATH" HOME="$HOME" node scripts/rehearse-cbt-protocol-fence.mjs /tmp/cbt-reconstruction-tools/node_modules/embedded-postgres/dist/index.js`

  This applies the 82 migrations, separately rehearses the non-migration deletion guard, and exercises the gateway rollback before the two older rollbacks. Both rehearsals use private Unix-socket PostgreSQL and synthetic users/questions, not production.
- Hosted review remains required for real Auth token verification/revocation, PostgREST JWT-to-role and claim settings, direct RPC exposure and schema cache, effective role membership and inherited privileges, database role creation/ownership and RLS, connection trust, and actual Netlify/server deployment configuration. A gateway role that an untrusted login can assume, or a PostgREST role/claim context that clients can forge, invalidates the trust argument. Direct authenticated wrapper access also bypasses Express-only capabilities and rate limits and must be explicitly approved.

## Regression results

- Local HTTP-to-PostgreSQL rehearsal and 82-migration role/rollback rehearsal passed. The HTTP test uses real Express and real migrated PostgreSQL through the synthetic compatibility gateway described above; it is not a hosted Supabase/PostgREST test.
